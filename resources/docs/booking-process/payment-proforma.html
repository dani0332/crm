❓ What is a Proforma Payment Request?

A Proforma Payment Request is a preliminary invoice document sent to customers to request payment before the actual policy invoice is issued. It serves as a payment requisition tool that helps track payment progress and provides customers with detailed payment information.

💡 Key Characteristics

Payment Structure:
• Always created with UPFRONT payment frequency
• Contains exactly ONE (1) payment split
• Single full-amount payment expected
• Not used for installment or progressive payment plans

Proforma vs Regular Invoice: Unlike a standard tax invoice, a proforma payment request is sent BEFORE payment is collected. It's an effective method for:

✓ Initiating payment requisitions from customers
✓ Tracking payment progress before policy finalization
✓ Providing payment details without issuing formal tax invoice
✓ Supporting upfront payment collection workflows

📋 Proforma Document Structure

The proforma payment request PDF contains comprehensive payment and policy information structured in a professional invoice format.

📌 Header Information

  • Company logo (InsuranceMarket.ae branding)
  • "Proforma Payment Request" title
  • Document reference code (payment.code)
  • Generation date (collection_date formatted)

👤 Customer Details

  • Customer name (insured or company)
  • Customer address (quote or entity address)
  • Customer reference ID (quote code)
  • Entity/company info (for business quotes)

💰 Payment Breakdown Table

  • Payment #: Always "1" (single upfront payment)
  • Due Date: collection_date from payment
  • Description: Quote type + insurance provider
  • Amount: Subtotal before VAT

📝 Payment Summary

  • Subtotal: price_vat_applicable
  • VAT: price_vat (calculated amount)
  • Discount: Only if discount_value > 0
  • Total Due: total_amount (final amount)
  • Remarks: payment.notes field

Special Data Sources

🔄 Main Lead Data

  • Uses quote model directly
  • For Car: actual_premium from car_quote_request_details
  • For others: price_vat_applicable from payment
  • Entity info from quoteRequestEntityMapping

📤 Send Update Data

  • Uses payment linked to send_update_log
  • Always uses price_vat_applicable from payment
  • References sendUpdateLog for versioning
  • No entity mapping for send updates

Database Schema

🗄️ Primary Tables

  • payments: Stores payment records with payment_methods_code = 'PPR'
  • payment_splits: Contains exactly 1 split record per proforma payment
  • quote_documents: Stores generated proforma PDFs with document_type_text
  • document_types: Contains 'Proforma Payment Request' document type
  • payment_methods: Defines 'PPR' payment method enum

🔑 Key Fields (payments table)

  • code: Unique payment reference (links payment & splits)
  • payment_methods_code: 'PPR' enum value
  • payment_frequency: Always 'UPFRONT' for proforma
  • price_vat_applicable: Amount before VAT
  • price_vat: VAT amount
  • total_amount: Final total (used in PDF)
  • collection_date: Due date shown on proforma
  • collection_type: 'BROKER' or 'INSURER'
  • notes: Remarks displayed on PDF
  • send_update_log_id: NULL for main lead, set for send updates

Document Storage (quote_documents table)

// Document record created in quote_documents $document = $docmentableTypeEntry->documents()->create([ 'doc_name' => $docName, // Unique name with uniqid prefix 'original_name' => $originalName, // User-friendly filename with version 'doc_url' => $filePathAzure, // Azure blob storage path 'doc_mime_type' => 'application/pdf', 'document_type_code' => 'PPR', // DocumentTypeCode::PPR 'document_type_text' => 'Proforma Payment Request', 'doc_uuid' => $this->helperService->generateUUID(), 'created_by_id' => auth()->id(), // Polymorphic fields automatically set: // quote_documentable_type => Quote model or SendUpdateLog // quote_documentable_id => quote.id or send_update_log.id ]);

🎯 Usage Scenarios

1. Main Lead (New Policy)

📝 Standard New Policy Flow

When creating a new policy with proforma payment request method:

Step 1: Select payment method = "Proforma Payment Request" during quote creation
Step 2: System creates payment record with payment_methods_code = 'PPR'
Step 3: Click "Create Proforma" button to generate PDF
Step 4: PDF stored in quote_documents with version number
Step 5: Download and send to customer for payment initiation

2. Send Update (Endorsements)

📝 Policy Amendment Flow

When policy changes require additional payment:

Step 1: Create send_update_log entry for policy changes
Step 2: Payment record linked to send_update_log via send_update_log_id
Step 3: Pass paymentCode parameter when generating proforma
Step 4: Version number increments for each send update proforma
Step 5: Separate proforma tracking per endorsement

3. Payment Frequency Configuration

💳 Upfront Payment with Single Split

Important: Proforma Payment Request is ALWAYS created with upfront payment frequency and contains only ONE (1) split payment.

Configuration:
• payment_frequency = 'UPFRONT'
• payment_splits table contains exactly 1 record
• Single proforma PDF generated for full amount
• Payment collected in one transaction

Why Single Split?
Proforma payment requests are preliminary invoices sent before payment is collected. The system creates one payment split record to track the single upfront payment transaction, maintaining consistency with the payment processing architecture.

📊 Payment Structure

  • 1 Payment Record: payment_methods_code = 'PPR'
  • 1 Payment Split: Single entry in payment_splits
  • 1 Proforma PDF: Generated for full amount
  • UPFRONT Frequency: Full payment expected immediately

🚫 Not Used For

  • Installment payments (monthly/quarterly)
  • Multiple split payment scenarios
  • Deferred payment schedules
  • Progressive payment plans

⚙️ Technical Constraints & Important Notes

🔒 Critical Payment Configuration

UPFRONT Frequency Requirement:
Proforma Payment Requests are strictly configured with the following constraints:

✓ payment_frequency MUST BE 'UPFRONT'
✓ payment_splits table CONTAINS EXACTLY 1 RECORD
✓ Single full-amount payment expected
✓ No installment or split payment support

Why This Matters:
This architectural decision ensures that proforma payment requests represent a single, complete payment transaction. The system creates one payment split record to maintain consistency with the payment processing architecture, even though the payment is upfront.

✅ Allowed Scenarios

  • Single upfront payment for full policy amount
  • One-time payment before policy issuance
  • Full payment collection in single transaction
  • Send update additional payments (also upfront)

❌ Not Supported

  • Monthly installment payments
  • Quarterly split payments
  • Multiple payment splits per proforma
  • Progressive payment schedules
-- Verify Proforma Payment Structure SELECT p.id, p.code, p.payment_methods_code, p.payment_frequency, p.total_price, COUNT(ps.id) as split_count FROM payments p LEFT JOIN payment_splits ps ON ps.code = p.code WHERE p.payment_methods_code = 'PPR' GROUP BY p.id; -- Expected Result: -- payment_methods_code: 'PPR' -- payment_frequency: 'UPFRONT' -- split_count: 1

📊 Version Tracking

Proforma payment requests support automatic version tracking for multiple document generations. Each time a proforma is regenerated, the version number increments.

// Version Calculation Logic (from ExportDocumentService.php) if ($isRequestFromSendUpdateLogPage) { // For Send Updates: Count versions per send_update_log $proformaPaymentRequestVersion = $sendUpdateLog->documents() ->where(['document_type_text' => DocumentTypeEnum::ProformaPaymentRequest]) ->count(); $docmentableTypeEntry = $sendUpdateLog; // Polymorphic relationship } else { // For Main Lead: Count versions per quote $proformaPaymentRequestVersion = $quote->documents() ->where(['document_type_text' => DocumentTypeEnum::ProformaPaymentRequest]) ->count(); $docmentableTypeEntry = $quote; // Polymorphic relationship } // Version number added to filename $pdfName = 'InsuranceMarket.ae™ Proforma Payment Request for ' . $quote->first_name . ' ' . $quote->last_name . '-' . $proformaPaymentRequest->code . '(' . ($proformaPaymentRequestVersion + 1) . ')' . '.pdf'; // Storage path structure $fileNameAzure = uniqid() . '_' . $docmentableTypeEntry->uuid . '_' . $docName; $filePathAzure = 'documents/' . ucwords($quoteType) . '/' . $fileNameAzure; // Example: documents/Car/60a1b2c3_car-uuid-123_InsuranceMarket.ae™ProformaPaymentRequest...pdf

📌 Version Scenarios

  • First generation: Version (1)
  • Regenerated for corrections: Version (2)
  • Send Update #1: Separate Version (1)
  • Each send update has independent versioning
  • Version count starts at 0, displays as (count + 1)

🗂️ Version Storage

  • All versions stored in quote_documents table
  • Historic versions remain accessible via doc_url
  • Latest version determined by created_at DESC
  • Audit trail maintained for compliance
  • Stored in Azure Blob Storage (azureIMPrivate disk)

Polymorphic Relationship

💡 Document Ownership

Quote Documents uses polymorphic relationship:

• Main Lead: quote_documentable_type = Quote Model (e.g., HealthQuote, TravelQuote)
• Send Update: quote_documentable_type = SendUpdateLog
• quote_documentable_id: References either quote.id or send_update_log.id

This allows versioning to be scoped correctly:

  • Main lead versions belong to quote
  • Each send update tracks its own proforma versions independently
  • Querying documents()->where() returns version count for correct scope

🔧 Troubleshooting

❌ Common Errors

  • "Proforma Payment Request not found": Payment with PPR method doesn't exist
  • Permission denied: User lacks proforma-create permission
  • File not found: Document deleted or S3 access issue
  • Invalid payment frequency: Payment not configured as UPFRONT
  • Multiple splits detected: More than 1 payment split exists (data integrity issue)

✅ Resolution Steps

  • Verify payment method = 'PPR' in payments table
  • Confirm payment_frequency = 'UPFRONT'
  • Check exactly 1 payment split exists for the payment
  • Validate user has correct permissions assigned
  • Confirm quote_documents entry exists with correct type
  • Validate S3 bucket configuration and credentials

🐛 Debug Checklist

If proforma generation fails:
1. Check logs: storage/logs/laravel.log for exceptions
2. Verify payment record: SELECT * FROM payments WHERE code = 'XXX'
3. Confirm payment method: payment_methods_code SHOULD BE 'PPR'
4. Verify payment frequency: payment_frequency MUST BE 'UPFRONT'
5. Check payment splits: SELECT COUNT(*) FROM payment_splits WHERE code = 'XXX' (should return 1)
6. Test PDF generation: Run createProformaPaymentRequestPdf() directly
7. Check blade template: Ensure proforma-invoice.blade.php is error-free
