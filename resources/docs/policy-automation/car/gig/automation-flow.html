💳 Pre-Automation Payment Capture

🔑 Critical Prerequisite Step

Auto-capture is a mandatory prerequisite that executes BEFORE the automation workflow begins. Payment must be successfully captured before automation can proceed.

Payment Flow

  1. Customer pays online → Payment authorized
  2. Background job processes → CcPaymentProcess handles split payment approval
  3. Auto-capture executes → SplitPaymentService->processSplitPaymentApprove() calls CRUDService->capturePayment()
  4. Marshall API call → Creates PaymentAction record with action_type: 'CAPTURE' and amount
  5. Success path: If capture succeeds → Automation workflow scheduled via createPolicyIssuanceAutomation()
  6. Failure path: If capture fails → handleAutomationError() sets insurer_api_status_id to AUTO_CAPTURE_FAILED_STATUS_ID and allocates to team

Implementation Details

  • Code Location: SplitPaymentService.php lines 770-792, 1475-1487
  • Retry Logic: Up to 3 attempts with 1-second delay between retries
  • Provider Support: Currently implemented for GIG (AXA) and potentially other providers
  • Failure Handling: If capture fails, automation is prevented from starting and quote is allocated for manual handling

⚠️ Important: This explains why documentation refers to "pre-captured" payments - the payment is already captured before any automation steps execute.

📋 Complete Automation Workflow Overview

The GIG Car Policy Issuance Automation follows a sequential 5-step process, where each step must complete successfully before proceeding to the next. The system maintains state throughout the process, includes OAuth authentication, batch OCR processing, and allows for retry mechanisms and manual intervention when needed.

Step 1

Upload Documents

Upload required documents (Car Registration Card, Emirates ID, Driving License) to GIG API. Documents are fetched from Azure Storage, base64 encoded, and uploaded with proper document type codes.

Step 2

Issue Policy

Create policy with GIG API using quote ID and payment details. Updates quote with policy number, dates, and syncs latest car quote information.

Step 3

Get & Upload Policy Docs

Download policy documents (Tax Invoice, Tax Invoice by Buyer, Receipt, Policy Schedule, Certificate of Insurance) from GIG and upload to IMCRM with proper document type mapping.

Step 4

Execute OCR Processing

Process policy documents through OCR batch jobs for data extraction. Uses Laravel batch jobs to process multiple documents in parallel, with callback handling for completion.

Step 5

Book Policy

Finalize booking process, update booking details with commission and payment information, validate prerequisites, and trigger Sage ERP integration.

💡 Workflow Characteristics

  • OAuth Authentication: OAuth 2.0 client credentials flow with Redis token caching
  • Sequential Execution: Steps execute in order, each dependent on the previous step's success
  • State Management: Completed steps are tracked in the PolicyIssuance model's completed_step field
  • Resumable: Failed automations can be resumed from the last completed step
  • Batch OCR Processing: Step 4 uses Laravel batch jobs for parallel document processing
  • Audit Trail: Every API call is logged in PolicyIssuanceLog for complete traceability
  • Error Recovery: Each step has specific error handling and can be retried independently

1️⃣ Step 1: Upload Documents

The first step uploads required customer documents to GIG's document management system. This includes Car Registration Card, Emirates ID, and Driving License. Documents are fetched from Azure Storage, validated, base64 encoded, and uploaded with proper document type codes.

📝 Process Flow

  1. OAuth Token Initialization: Initialize OAuth access token from Redis cache or fetch new token if expired
  2. Document Validation: Validate required documents exist using PolicyIssuanceService::documentUploadPreChecks():
    • Car Registration Card (CAR_REGISTRATION_CARD) → DT01
    • Emirates ID (CAR_EMIRATE_ID) → DT03
    • Driving License (DRIVING_LICENSE) → DT02
  3. Document Fetching: For each required document type, fetch all documents from Azure Storage using Storage::disk('azureIMPrivate')->get(). Supports multiple documents per type (e.g., Emirates ID front/back).
  4. Base64 Encoding: Convert document content to base64 encoding for API transmission
  5. Payload Construction: Build upload payload with:
    • referenceType: 'quotation'
    • referenceValue: Quote's insurer quote number
    • documentType: Object with code and value:
      • DT01: Car Registration Document (Mulkiya)
      • DT02: Driving License
      • DT03: National ID (Emirates ID)
    • documentContent: Base64 encoded document content
    • documentName: Unique document name
    • mimeType: Document MIME type
  6. API Call: Call GIG API endpoint /v1/insurance-documents via POST for each document. All documents of a type must succeed for that type to be marked as uploaded.
  7. Response Validation: Parse response and track upload status for each document type. Track success per document type; all documents of a type must succeed.
  8. API Log Storage: Store API log for each document upload attempt in PolicyIssuanceLog
  9. Step Completion: Mark step as completed only if all required documents uploaded successfully (completed_step = UploadDocuments)

✅ Success Criteria

  • OAuth access token successfully obtained and cached in Redis
  • All three required document types are successfully uploaded to GIG
  • Each document upload API call returns HTTP 200 with success confirmation
  • Document type codes are correctly mapped (DT01, DT02, DT03)
  • All documents pass MIME type validation
  • Step is marked as completed (completed_step = UploadDocuments)
  • API logs are stored for each document upload with SUCCESS_STATUS
  • LoggerService logs successful completion with document count and types

❌ Failure Handling

  • OAuth Token Failure: Return error if token cannot be obtained; log authentication failure
  • Missing Documents: Return error with specific document names; log missing document types
  • Azure Storage Error: Log storage connectivity issues; return error with document fetch failure details
  • Document Upload Failure: Track failed documents per type; log detailed error including document name and API error
  • Partial Success: If some documents succeed but others fail, mark step as incomplete; log partial success details with counts
  • API Timeout: Handle timeout per document; allow retry for failed documents only

📄 Document Type Mapping

  • Car Registration Card (DT01): CAR_REGISTRATION_CARD → 'Car Registration Document'
  • Driving License (DT02): DRIVING_LICENSE → 'Driving License'
  • National ID (DT03): CAR_EMIRATE_ID → 'National ID'

2️⃣ Step 2: Issue Policy

The second step creates a policy with GIG Insurance Company using quote information and payment details. This step establishes the policy foundation and generates the policy number. Note: Payment is PRE-CAPTURED before automation starts; only payment amount and mode are sent (NO transaction_id used).

📝 Process Flow

  1. Prerequisite Check: Validate that Step 1 (Upload Documents) completed successfully
  2. OAuth Token: Ensure valid OAuth access token is available
  3. Payment Retrieval: Get main lead payment from quote using $quote->payments()->mainLeadPayment()->first(). Payment is already authorized/captured before automation starts.
  4. Payload Construction: Build issue policy payload:
    • quoteId: Quote's insurer quote number
    • isActive: 'true'
    • payment: Object with payment mode and amount:
      • paymentMode.code: 'CT068' (Upfront Commission Partner Payment)
      • paymentMode.value: 'Upfront Commission Partner Payment'
      • paymentAmount.amount: $payment->total_amount in AED currency
      • paymentAmount.currencyCode: 'AED'
      • Note: NO transaction_id is used or sent
  5. API Call: Call GIG API endpoint /v3/policies via POST
  6. Response Parsing: Parse API response and extract policy ID
  7. Quote Update: Update quote with:
    • Policy number (policy_number)
    • Quote status (PolicyIssued)
    • Policy issuance status (PolicyIssued)
    • Quote status date
  8. Sync Car Quote Info: Sync latest car quote information to quote using CentralService::syncLatestCarQuoteInfoToQuote()
  9. API Log Storage: Store complete API request and response in PolicyIssuanceLog
  10. Step Completion: Mark step as completed (completed_step = IssuePolicy)

✅ Success Criteria

  • API returns HTTP 200 status code with successful response
  • Policy ID is generated and present in response
  • Quote record is updated with policy number and status
  • Car quote information is synced successfully
  • Step is marked as completed (completed_step = IssuePolicy)
  • API log is stored with SUCCESS_STATUS
  • LoggerService logs successful completion

❌ Failure Handling

  • Prerequisite Failure: Return error if Step 1 not completed; log prerequisite validation error
  • OAuth Token Expired: Attempt to refresh token; if fails, return authentication error
  • API Error: Log detailed error including endpoint, payload, and error message; update insurer API status to failed
  • HTTP Exception: Catch and log exception with full context; update process status; return error response
  • Invalid Response: Validate response structure; log parsing errors; return error with specific message

3️⃣ Step 3: Get & Upload Policy Documents to IMCRM

The third step downloads policy documents from GIG (Tax Invoice, Tax Invoice by Buyer, Receipt, Policy Schedule, Certificate of Insurance) and uploads them to IMCRM's document management system. These documents are generated by GIG after policy issuance.

📝 Process Flow

  1. Prerequisite Check: Validate that Step 2 (Issue Policy) completed successfully
  2. Policy Issuance Response: Retrieve policy issuance response from PolicyIssuanceLog where step = IssuePolicy and status = SUCCESS_STATUS
  3. Document List Extraction: Extract policy documents array and policy ID from response
  4. Download Loop: For each document in the policy documents array:
    • Skip Certificate of Insurance in non-production environments (handled separately - duplicated from Policy Schedule)
    • Skip Commission statement documents
    • Build download headers with document ID, reference type ('policy'), and reference value (policy ID):
      • opCo: 'UAE'
      • documentType: Document ID from policy issuance response
      • referenceType: 'policy'
      • referenceValue: Policy ID
    • Call GIG API endpoint /v1/insurance-documents/document via GET with headers
    • Wait 10 seconds between document downloads (rate limiting)
    • Parse response and extract base64 document content (base64 decoded before storage)
    • Map document name to IMCRM document type codes:
      • 'Tax invoice' → TI (Tax Invoice)
      • 'Tax invoice by buyer' → CTIRBB (Tax Invoice Raised By Buyer)
      • 'Receipt with reference' → CPD_RECEIPT
      • 'Motor Insurance Policy Schedule' → CPS (Policy Schedule)
      • 'Certificate of Insurance' → CPC (Certificate)
    • Upload to IMCRM using uploadAndAttachToQuoteDocuments()
    • Trigger watermark job for uploaded document
    • Store API log for download operation
  5. Certificate of Insurance Handling:
    • Production: Fetched from API
    • Non-production: Duplicated from Policy Schedule (for testing)
    • Update rta_upload_status when certificate is available
  6. Validation: Verify all documents downloaded and uploaded successfully
  7. Step Completion: Mark step as completed (completed_step = GetAndUploadPolicyDocumentsToIMCRM)

✅ Success Criteria

  • All policy documents are successfully downloaded from GIG
  • All documents are successfully uploaded to IMCRM
  • Document type codes are correctly mapped to IMCRM codes
  • Certificate of Insurance is available and RTA upload status is updated
  • Watermark jobs are dispatched for all uploaded documents
  • Step is marked as completed
  • API logs are stored for each document download with SUCCESS_STATUS

❌ Failure Handling

  • Prerequisite Failure: Return error if Step 2 not completed
  • Policy Issuance Response Not Found: Return error with message about missing response
  • Document Download Failure: Log error for specific document; continue with other documents
  • Document Mapping Failure: Log warning for unmapped document types; skip upload
  • IMCRM Upload Failure: Log error for specific document; track failed documents
  • Certificate of Insurance Missing: Update RTA upload status to pending; log warning

4️⃣ Step 4: Execute OCR Processing

The fourth step processes policy documents through OCR (Optical Character Recognition) batch jobs for data extraction. This step uses Laravel batch jobs to process multiple documents in parallel, with callback handling for completion and error recovery.

📝 Process Flow

  1. Prerequisite Check: Validate that Step 3 (Get & Upload Policy Documents) completed successfully
  2. Document Retrieval: Get policy documents that were uploaded in Step 3:
    • Filter by document type codes: TI (Tax Invoice) and CTIRBB (Tax Invoice Raised By Buyer) only
    • Filter documents created within 30 minutes of step completion
  3. Document Validation: Verify documents exist; return error if no documents found
  4. Batch Job Creation: Create Laravel Bus batch job for OCR processing:
    • Get API automation user (happiness user)
    • For each document, create PopulateDocumentData job with:
      • Quote type (Car)
      • Quote model
      • Document type model
      • Document URL
      • Document MIME type
      • User ID
  5. Batch Dispatch: Dispatch batch with callbacks:
    • then() callback: On complete success, update process:
      • Set completed_step = ExecuteOCRProcessing
      • Set status = BOOKING_PENDING_STATUS
      • Log completion
    • catch() callback: On complete failure, update status to failed and log error
    • finally() callback: Log batch completion with statistics
    • Set allowFailures() to handle partial failures
    • Dispatch on 'shared' queue
  6. Response Handling: Return response indicating OCR processing is in progress

✅ Success Criteria

  • OCR batch is successfully dispatched with all document jobs
  • All OCR jobs complete successfully
  • Batch callback updates process status to BOOKING_PENDING_STATUS
  • Step is marked as completed (completed_step = ExecuteOCRProcessing)
  • LoggerService logs batch dispatch and completion

❌ Failure Handling

  • No Documents Found: Return error if no policy documents found for OCR processing
  • Batch Dispatch Failure: Log exception; return error response
  • Partial Batch Failure: Batch callback logs statistics; process continues if allowFailures() is set
  • Complete Batch Failure: catch() callback updates status to failed; logs error
  • OCR Job Failure: Individual job failures are logged; batch continues with other jobs

🔑 Key Features

  • Parallel Processing: Multiple documents processed simultaneously using Laravel batch jobs
  • Callback Handling: then(), catch(), and finally() callbacks for comprehensive error handling
  • Partial Failure Tolerance: allowFailures() allows batch to complete even if some jobs fail
  • Status Management: Process status updated based on batch completion
  • Queue Processing: Jobs dispatched on 'shared' queue for load distribution

5️⃣ Step 5: Book Policy

The final step completes the booking process by updating booking details with commission and payment information, validating prerequisites, and triggering Sage ERP integration for final processing.

📝 Process Flow

  1. Prerequisite Check: Validate that Step 4 (Execute OCR Processing) completed successfully
  2. Update Commission: Update commission details using ManualCommissionUpdateService::updateCommissionForLeads()
  3. Payment Retrieval: Get main lead payment from quote
  4. Booking Payload Construction: Build booking payload with:
    • Invoice date, tax invoice number, commission invoice number
    • Discount value, transaction payment status
    • Broker invoice number
    • Commission VAT details (applicable/not applicable)
    • Total commission, VAT on commission, commission percentage
    • Payment code, model type, quote ID
  5. Booking Details Validation: Validate booking payload using BookPolicyRequest validation rules
  6. Update Booking Details: Update booking details using CentralService::updateBookingDetails()
  7. Book Policy Validation: Validate book policy prerequisites using SendBookPolicyRequest validation
  8. Sage Integration: Trigger Sage ERP integration using SageApiService::postBookPolicyToSage():
    • Create request object with quote ID, model type, send policy type (SAGE)
    • Set is_send_policy = false
    • Call Sage API to create booking process
  9. API Log Storage: Store Sage API request and response in PolicyIssuanceLog
  10. Step Completion: Mark step as completed (completed_step = BookPolicy)

✅ Success Criteria

  • Commission details updated successfully
  • Booking details validation passes
  • Booking details updated in database
  • Book policy prerequisites validated successfully
  • Sage ERP process created successfully
  • Step is marked as completed (completed_step = BookPolicy)
  • API log is stored with SUCCESS_STATUS
  • LoggerService logs successful completion

❌ Failure Handling

  • Prerequisite Failure: Return error if Step 4 not completed
  • Commission Update Failure: Log error but continue (non-blocking)
  • Validation Failure: Return error with specific validation errors
  • Booking Update Failure: Log error; return error response
  • Sage Integration Failure: Log detailed error; update insurer API status to failed; return error
  • Exception: Catch and log exception with full context; return error response

🔑 Key Data Updates

  • Payment: Commission amounts, VAT details, invoice numbers
  • Quote: Booking status, transaction payment status
  • PolicyIssuance: completed_step = BookPolicy
  • Sage Process: Booking process created in Sage ERP system

📊 State Management

The automation system maintains state throughout the process using the PolicyIssuance model. This allows for resumable workflows, error recovery, and progress tracking.

Process States

  • PENDING_STATUS: Automation scheduled but not yet started
  • PROCESSING_STATUS: Currently executing automation steps
  • BOOKING_PENDING_STATUS: OCR processing completed, waiting for booking
  • TIMEOUT_STATUS: Process timed out, eligible for retry if retry enabled
  • FAILED_STATUS: Process failed, requires manual intervention

Completed Steps

  • null: No steps completed
  • UploadDocuments: Documents uploaded to GIG
  • IssuePolicy: Policy created with GIG
  • GetAndUploadPolicyDocumentsToIMCRM: Policy documents retrieved and uploaded
  • ExecuteOCRProcessing: OCR processing completed
  • BookPolicy: Booking process completed
