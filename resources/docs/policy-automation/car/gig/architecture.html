📋 Overview

The GIG Car Policy Issuance Automation system follows a monolithic service architecture where GIGInsuranceService implements the PolicyIssuanceInterface and handles all aspects of the automation workflow. Unlike the ADNIC Health implementation which uses multiple specialized services, GIG Car uses a single service class with integrated OAuth authentication, HTTP communication, and batch OCR processing.

Core Purpose

  • Automate the entire car policy issuance lifecycle from document upload to booked policy
  • Provide OAuth 2.0 authentication with Redis token caching
  • Handle batch OCR processing for policy documents
  • Maintain data integrity and audit trails throughout the automation process
  • Enable seamless integration with GIG Insurance APIs

Key Features

OAuth 2.0 Authentication: Client credentials flow with Redis token caching
Monolithic Service: Single service class handling all automation steps
Batch OCR Processing: Laravel batch jobs for parallel document processing
Comprehensive Logging: Detailed audit trails using LoggerService
Retry Mechanisms: Handles timeouts and transient failures
Document Management: Azure Storage integration for document handling
Status Tracking: Real-time tracking of automation progress
Queue-based Processing: Asynchronous batch job processing

🔐 OAuth 2.0 Authentication

Token Management Flow

1. Check Redis Cache for existing token ├── Token exists and valid → Use cached token └── Token missing/expired → Fetch new token ├── Call OAuth endpoint (/oauth/token) ├── Extract access_token and expires_in ├── Cache token in Redis with TTL └── Return access token

OAuth Configuration

// OAuth Endpoint authUrl: {GIG_API_AUTH_BASE_URL}/oauth/token // Request Payload { 'client_id': {GIG_API_AUTH_CLIENT_ID}, 'client_secret': {GIG_API_AUTH_CLIENT_SECRET}, 'grant_type': 'client_credentials', 'audience': 'integration-platform' } // Response { 'access_token': '...', 'expires_in': 3600, 'token_type': 'Bearer' }

Token Caching

  • Cache Key: AXA_POLICY_ISSUANCE_API_ACCESS_TOKEN
  • Cache Store: Redis
  • TTL: Set from expires_in response field
  • Token Refresh: Automatic refresh when token expires or missing
Benefits:
  • Reduces API calls to OAuth endpoint
  • Improves performance by avoiding token fetch on every request
  • Automatic token refresh ensures continuous operation
  • Redis caching provides fast token retrieval

📄 Batch OCR Processing

OCR Batch Architecture

executeOCRProcessing() ├── Get policy documents (TI, CTIRBB) ├── Create PopulateDocumentData jobs │ ├── Job 1: Tax Invoice OCR │ ├── Job 2: Tax Invoice by Buyer OCR │ └── ... ├── Dispatch Laravel Batch │ ├── then() callback → Update status on success │ ├── catch() callback → Handle complete failure │ └── finally() callback → Log statistics └── Return processing status

Batch Job Configuration

Bus::batch($documentOCRJobs) ->then(function (Batch $batch) { // All jobs completed successfully // Update process status to BOOKING_PENDING_STATUS // Mark step as completed }) ->catch(function (Batch $batch, Throwable $e) { // Complete batch failure // Update status to FAILED_STATUS // Log error }) ->finally(function (Batch $batch) { // Always executed // Log batch statistics }) ->allowFailures() // Allow partial failures ->onQueue('shared') ->dispatch();

OCR Job Details

  • Job Class: PopulateDocumentData
  • Parameters: Quote type, Quote model, Document type, Document URL, MIME type, User ID
  • Queue: 'shared' queue for load distribution
  • Failure Handling: Partial failures allowed, complete failure triggers catch callback

🎨 Design Patterns & Principles

1. Strategy Pattern

GIGInsuranceService implements PolicyIssuanceInterface, providing a provider-specific strategy for car insurance automation.

2. Monolithic Service Pattern

Unlike ADNIC's multi-service architecture, GIG uses a single service class that handles all aspects of automation, providing simplicity and cohesion.

3. Chain of Responsibility

Step execution flows sequentially through the service:

executeSteps() → executeStepSequence() → executeUploadDocumentsStep() → executeIssuePolicyStep() → ...

4. Facade Pattern

httpCall() method provides a simplified interface to Laravel's HTTP client, abstracting retry logic, headers, and error handling.

5. Builder Pattern

Payload construction methods build complex API request payloads step-by-step (e.g., document upload payload, policy issuance payload).

6. Observer Pattern

Laravel batch jobs use callbacks (then, catch, finally) to observe batch completion and update process state accordingly.

📝 Key Implementation Details

1. OAuth Token Initialization

private function initializeAccessToken(): bool { // Check Redis cache first $this->accessToken = Cache::store('redis') ->get(self::POLICY_ISSUANCE_API_ACCESS_TOKEN_KEY); // Fetch new token if not cached if (!$this->accessToken) { $this->accessToken = $this->getAccessToken(); } return $this->accessToken !== null; }

2. Step Execution Sequence

private function executeStepSequence($quote, $process, $nextStepToBeExecuted) { // Step 1: Upload Documents if ($nextStepToBeExecuted === self::UPLOAD_DOCUMENTS) { $response = $this->executeUploadDocumentsStep($quote, $process); if (!$response['status']) return $response; $nextStepToBeExecuted = $this->getNextStep($process->completed_step); } // Step 2: Issue Policy if ($nextStepToBeExecuted === self::ISSUE_POLICY) { // ... continue with next steps } // Continue for all 5 steps... }

4. Batch OCR Dispatch

private function dispatchPopulateDocumentDataBatch($quote, $uploadedDocuments, $process): void { $documentOCRJobs = []; foreach ($uploadedDocuments as $document) { $documentOCRJobs[] = new PopulateDocumentData( QuoteTypes::CAR, $quote, $documentType, $document->doc_url, $document->doc_mime_type, $happinessUser->id ); } Bus::batch($documentOCRJobs) ->then(function (Batch $batch) use ($quote, $process) { $process->update([ 'completed_step' => self::EXECUTE_OCR_PROCESSING, 'status' => PolicyIssuanceEnum::BOOKING_PENDING_STATUS, ]); }) ->allowFailures() ->onQueue('shared') ->dispatch(); }
