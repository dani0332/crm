🔌 ADNIC API Integration

Complete API Documentation for ADNIC Health Insurance Policy Issuance

🔐 Authentication & Authorization

All ADNIC API requests require authentication using header-based credentials. The API uses a combination of Bearer token and subscription key for authentication.

Authentication Method Header-based authentication with Bearer token and Azure API Management subscription key
⚠️ Important Requirements
  • STP Cases Only: Automation only runs for STP cases ($quote->isSTPCase())
  • Pre-Captured Payment: Payment must be authorized before automation starts
  • Transaction ID: Used as PaymentRefNo from $splitPayment?->paymentCharges?->transaction_id

Required Headers

Header Name Description Example
Authorization Bearer token or authorization token provided by ADNIC Bearer {TOKEN} or {TOKEN}
Ocp-Apim-Subscription-Key Azure API Management subscription key {SUBSCRIPTION_KEY}
Content-Type Request content type (always JSON) application/json
Accept Expected response format application/json

Header Structure Example

{
  "Content-Type": "application/json",
  "Accept": "application/json",
  "Ocp-Apim-Subscription-Key": "your_subscription_key_here",
  "Authorization": "Bearer your_authorization_token_here"
}

Configuration

Authentication credentials are configured via environment variables:

Authorization Token ADNIC_AUTHORIZATION_TOKEN

Bearer token or authorization token

Subscription Key ADNIC_SUBSCRIPTION_KEY

Azure API Management subscription key

Partner ID ADNIC_PARTNER_ID

Partner identifier for API requests

Partner Reference No ADNIC_PARTNER_REFERENCE_NO

Partner reference number

🌐 API Base URL & Configuration

Base URL Structure

{ADNIC_API_BASE_URL}/dev/MedicalProductAPI/MedicalAPI.svc/API/Medical
Environment Variable ADNIC_API_BASE_URL - Base URL for ADNIC API (e.g., https://api.adnic.ae)

API Timeout Configuration

API timeout is configurable via ApplicationStorage runtime configuration:

Timeout Configuration ADNIC_HEALTH_AUTOMATION_API_TIMEOUT

Timeout in seconds (default: configurable via ApplicationStorage)

⚠️ Important Timeout values are retrieved from ApplicationStorage at runtime, allowing configuration changes without code deployment.

Retry Configuration

The HTTP client implements automatic retry logic for connection and timeout errors:

  • Retry Attempts: 5 times
  • Retry Delay: 10 seconds between attempts
  • Retry Conditions: Connection exceptions and timeout errors

Request Headers

Ocp-Apim-Subscription-Key: {SUBSCRIPTION_KEY}
Authorization: {AUTHORIZATION_TOKEN}

Request Payload Fields

Field Type Required Description
PartnerInfo.PartnerId string Yes Partner identifier
DocumentInfo.QuotationNo string Yes Quotation number
DocumentInfo.MemberSeqNo integer Yes Member sequence number. Documents are uploaded per-member, meaning each insured member's documents are uploaded separately.

DocumentInfo.DocumentUploadDate string Yes ISO 8601 formatted upload date
DocumentInfo.IsDocumentValidated string Yes Validation flag: "Y" or "N"

POST /GeneratePolicyDocument

Purpose

Downloads policy documents (Policy Schedule, Tax Invoice, Tax Invoice Raised By Buyer) from ADNIC as base64-encoded PDF files. All 3 documents must be successfully downloaded and uploaded for the step to pass.

Request Headers

Content-Type: application/json
Accept: application/json
Ocp-Apim-Subscription-Key: {SUBSCRIPTION_KEY}
Authorization: {AUTHORIZATION_TOKEN}

Request Payload Structure

{
  "PartnerInfo": {
    "PartnerId": "PARTNER_ID"
  },
  "PolicyDocumentInfo": {
    "PartnerReferenceNo": "REF123",
    "QuotationNo": "QUOTE123",
    "PolicyNo": "POL123456",
    "DocumentId": "POLDOC123"
  }
}

Request Payload Fields

Field Type Required Description
PartnerInfo.PartnerId string Yes Partner identifier
PolicyDocumentInfo.PartnerReferenceNo string Yes Partner reference number
PolicyDocumentInfo.QuotationNo string Yes Quotation number
PolicyDocumentInfo.PolicyNo string Yes Policy number from GeneratePolicy response
PolicyDocumentInfo.DocumentId string Yes Document ID from GeneratePolicy response (PolicyDocumentId, CommisionNoteDocumentId, or TaxInvoiceDocumentId)
📋 Document Types Retrieved
  • Policy Schedule: PolicyDocumentId → Mapped to IMCRM code: POLICY_SCHEDULE
  • Tax Invoice Raised By Buyer: CommisionNoteDocumentId → Mapped to IMCRM code: CTIRBB
  • Tax Invoice: TaxInvoiceDocumentId → Mapped to IMCRM code: TI
  • All 3 Required: All three documents must be successfully downloaded and uploaded. Step fails if any document fails.

Success Response (HTTP 200)

{
  "DocumentInfo": {
    "documentContent": "JVBERi0xLjQKJeLjz9MKMSAwIG9iago8PC9MZW5ndGggMiAwIFIvRmlsdGVyL0ZsYXRlRGVjb2RlPj4Kc3RyZWFtCngBXZ...",
    "documentName": "Policy_POL123456.pdf",
    "documentType": "Policy"
  }
}

Response Fields

Field Type Description
DocumentInfo.documentContent string Base64 encoded PDF document content
DocumentInfo.documentName string Document filename
DocumentInfo.documentType string Document type (Policy, Commission Note, Tax Invoice)

Error Response

{
  "DocumentInfo": {
    "ErrorInfo": [
      {
        "ErrorCode": "E004",
        "ErrorMsg": "Document not found"
      }
    ]
  }
}

⚠️ Error Handling

HTTP Status Codes

Status Code Description Handling
200 OK Request successful Check response body for API-level errors in ErrorInfo array
404 Not Found Endpoint not found Verify endpoint URL and base URL configuration
500 Internal Server Error Server error Retry with exponential backoff
Timeout Request timeout Automatic retry (5 attempts, 10s delay) if retry enabled

API-Level Error Detection

The response handler checks for errors in the following order:

  1. Null Response: If response object is null, treat as error
  2. ErrorInfo Array: Check for ErrorInfo array at root level
  3. Nested ErrorInfo: Check for DocumentInfo.ErrorInfo array

Error Response Structure

{
  "ErrorInfo": [
    {
      "ErrorCode": "E001",
      "ErrorMsg": "Error message description"
    }
  ]
}

Nested Error Response Structure

{
  "DocumentInfo": {
    "ErrorInfo": [
      {
        "ErrorCode": "E002",
        "ErrorMsg": "Document validation failed"
      }
    ]
  }
}

Error Extraction Logic

// Error detection priority:
1. Check if responseObject == null → Error
2. Check if ErrorInfo array exists and has items → Extract ErrorInfo[0].ErrorMsg
3. Check if DocumentInfo.ErrorInfo array exists → Extract DocumentInfo.ErrorInfo[0].ErrorMsg
4. Default error message: "{API_KEY} API Failed"
⚠️ Important Even if HTTP status is 200, always check the response body for API-level errors. A successful HTTP response does not guarantee a successful API operation.

✅ Best Practices

Request Handling

  • Always validate data before making API calls
  • Use pre-validation to prevent unnecessary API requests
  • Format dates as dd-mm-yyyy for policy dates
  • Ensure document content is properly base64 encoded
  • Include all required fields in request payloads

Response Handling

  • Always check for API-level errors even on HTTP 200
  • Parse error messages from ErrorInfo arrays
  • Store API logs for audit trails
  • Extract document IDs from upload responses
  • Validate document IDs exist before download requests

Error Handling

  • Implement retry logic for timeout errors
  • Log all API errors with context
  • Update status appropriately on failures
  • Handle null responses gracefully
  • Check nested error structures (DocumentInfo.ErrorInfo)

Security

  • Never log sensitive credentials
  • Store credentials in environment variables
  • Validate document MIME types before upload
  • Use secure storage for document content
  • Implement proper access controls
