🔄 ADNIC Health Automation Flow

Complete 3-Step Policy Issuance Workflow with Detailed Process Documentation

💳 Pre-Automation Payment Capture

🔑 Critical Prerequisite Step

Auto-capture is a mandatory prerequisite that executes BEFORE the automation workflow begins. Payment must be successfully captured before automation can proceed.

Payment Flow

  1. Customer pays online → Payment authorized
  2. Background job processes → CcPaymentProcess handles split payment approval
  3. Auto-capture executes → SplitPaymentService->processSplitPaymentApprove() calls CRUDService->capturePayment()
  4. Marshall API call → Creates PaymentAction record with action_type: 'CAPTURE' and amount
  5. Success path: If capture succeeds → Automation workflow scheduled via createPolicyIssuanceAutomation()
  6. Failure path: If capture fails → handleAutomationError() sets insurer_api_status_id to AUTO_CAPTURE_FAILED_STATUS_ID and allocates to team

Implementation Details

  • Code Location: SplitPaymentService.php lines 770-792, 1475-1487
  • Retry Logic: Up to 3 attempts with 1-second delay between retries
  • Provider Support: Currently implemented for ADNIC Health and other e-commerce providers
  • Failure Handling: If capture fails, automation is prevented from starting and quote is allocated for manual handling

⚠️ Important: This explains why documentation refers to "pre-captured" payments - the payment is already captured before any automation steps execute.

📋 Complete Automation Workflow Overview

The ADNIC Health Policy Issuance Automation follows a sequential 3-step process for STP cases only, where each step must complete successfully before proceeding to the next. Payment is pre-captured before automation starts. The system maintains state throughout the process, allowing for retry mechanisms and manual intervention when needed.

Step 1

Upload Documents

Upload required customer documents per member (Emirates ID, Passport, etc.) to ADNIC's document management system. Each insured member's documents are uploaded separately.

Step 2

Issue Policy

Create policy with ADNIC API using customer and plan details with pre-captured payment reference (transaction ID). Updates quote with policy number, dates, and amounts.

Step 3

Upload Policy Docs to IMCRM

Download all 3 policy documents from ADNIC (Tax Invoice, Tax Invoice Raised By Buyer, Policy Schedule) and upload to IMCRM. All 3 documents must succeed for this step to pass.

💡 Workflow Characteristics

  • STP-Only: Automation only runs for STP cases ($quote->isSTPCase())
  • Pre-Captured Payment: Payment is already authorized before automation starts; transaction ID used as PaymentRefNo
  • Per-Member Upload: Documents are uploaded separately for each insured member
  • Sequential Execution: Steps execute in order, each dependent on the previous step's success
  • State Management: Completed steps are tracked in the PolicyIssuance model's completed_step field
  • Resumable: Failed automations can be resumed from the last completed step
  • Audit Trail: Every API call is logged in PolicyIssuanceLog for complete traceability
  • Error Recovery: Each step has specific error handling and can be retried independently
  • All 3 Documents Required: Step 3 requires all 3 policy documents to succeed

1️⃣ Step 1: Upload Documents

The first step uploads required customer documents to ADNIC's document management system. Documents are uploaded per-member, meaning each insured member's documents are uploaded separately with their MemberSeqNo. This typically includes Emirates ID, Passport, and other required documents based on the policy type.

📝 Process Flow

  1. STP Case Validation: Validate that quote is an STP case using $quote->isSTPCase() - automation only runs for STP cases
  2. Document Validation: Validate required documents are uploaded (Emirates ID, Passport, etc.) using AdnicValidationService::validateUploadDocuments()
  3. Member Loop: For each insured member in the quote:
    • Get member sequence number (MemberSeqNo)
    • Fetch member-specific documents from Azure Storage
    • Validate document MIME types (PDF, JPEG, PNG)
    • Convert document content to base64 encoding
    • Build upload payload with member sequence number
    • Call ADNIC API endpoint /UploadDocument via AdnicApiService::uploadDocuments()
    • Store API log for each document upload
  4. Validation Check: Verify Emirates ID front and back are both uploaded (if applicable)
  5. Step Completion: Mark step as completed only if all required documents for all members uploaded successfully (completed_step = STEP_UPLOAD_DOCUMENTS)

✅ Success Criteria

  • Quote is validated as STP case
  • All required documents for all insured members are successfully uploaded to ADNIC
  • Each document upload API call returns HTTP 200 with success confirmation

  • API logs are stored for each document upload with SUCCESS_STATUS
  • LoggerService logs successful completion with document count and member details

❌ Failure Handling

  • Non-STP Case: Return error if quote is not STP case; log STP validation error
  • Missing Documents: Return error with specific document names and member details; log missing document types
  • Azure Storage Error: Log storage connectivity issues; return error with document fetch failure details
  • Invalid MIME Type: Reject document and log error; return specific document name, member, and invalid type
  • Document Upload Failure: Stop on first failed document; log detailed error including document name, member, and API error; update insurer API status
  • Partial Success: If some documents succeed but others fail, mark step as incomplete; log partial success details per member
  • API Timeout: Handle timeout per document; allow retry for failed documents only

📄 Document Types

  • Emirates ID (HEA_EID): Required for all health policies - uploaded per member
  • Passport (HEA_PAS): Required document - uploaded per member
  • Visa (HEA_VISA): May be required based on policy type - uploaded per member
  • Other Documents: Birth Certificate, Medical Application Form, Customer Due Diligence - uploaded per member
  • Document Mapping: Document types are mapped from IMCRM codes to ADNIC-specific codes using AdnicDocumentHandler::getDocTypeCodeForHealth()
  • Per-Member Upload: Each insured member's documents are uploaded separately with their MemberSeqNo

2️⃣ Step 2: Issue Policy

The second step creates a policy with ADNIC Insurance Company using customer information, plan details, and pre-captured payment data. Payment is already authorized before automation starts, and the transaction ID is used as PaymentRefNo in the API call. This step establishes the policy foundation and generates the policy number.

📝 Process Flow

  1. Prerequisite Check: Validate that Step 1 (Upload Documents) completed successfully by checking completed_step
  2. Pre-Validation: Validate required data including customer details, nationality, plan information, and payment data using AdnicValidationService::validateRequiredData()
  3. Payment Reference: Extract transaction ID from pre-captured payment: $splitPayment?->paymentCharges?->transaction_id
  4. Payload Construction: Build issue policy payload with customer and plan details, including PaymentRefNo (transaction ID) using AdnicRequestBuilder::buildIssuePolicyPayload()
  5. API Call: Call ADNIC API endpoint /GeneratePolicy via AdnicApiService::issuePolicy()
  6. Response Parsing: Parse API response and extract policy details (policy number, dates, amounts, document IDs) using AdnicResponseHandler::parseHttpResponse()
  7. Quote Update: Update quote with policy number, policy start date, policy end date, and premium amounts using AdnicQuoteUpdaterService::updateQuoteFromIssuePolicyResponse()
  8. Document IDs Storage: Store document IDs from response (Tax Invoice, Tax Invoice Raised By Buyer, Policy Schedule) in quote record
  9. API Log Storage: Store complete API request and response in PolicyIssuanceLog for audit trail
  10. Step Completion: Mark step as completed by updating PolicyIssuance.completed_step to STEP_ISSUE_POLICY

  • Policy number is generated and present in response

❌ Failure Handling

  • Prerequisite Failure: Return error if Step 1 not completed; log prerequisite validation error
  • Validation Failure: Return error response immediately without API call, log validation errors
  • Missing Payment Reference: Return error if transaction ID not found; log payment reference error
  • API Error: Log detailed error including endpoint, payload keys, and error message; update insurer API status to failed; store failed log
  • HTTP Exception: Catch and log exception with full context; update process status; return error response
  • Timeout: If retry enabled, mark process as TIMEOUT_STATUS for retry; otherwise mark as FAILED_STATUS
  • Invalid Response: Validate response structure; log parsing errors; return error with specific message
  • Database Update Failure: Log database errors; maintain API success but flag update failure; allow manual intervention

🔑 Key Data Updates

  • Quote: Policy number, policy start date, policy end date, premium amounts, document IDs (tax invoice, tax invoice raised by buyer, policy schedule)
  • Payment Reference: Transaction ID from $splitPayment?->paymentCharges?->transaction_id used as PaymentRefNo
  • PolicyIssuance: completed_step = STEP_ISSUE_POLICY
  • PolicyIssuanceLog: Complete request/response payload, endpoint URL, status, timestamp
  • Payment Status: Payment is PRE-CAPTURED before automation starts - no payment capture in this step

3️⃣ Step 3: Upload Policy Documents to IMCRM

The third step downloads all 3 policy documents (Tax Invoice, Tax Invoice Raised By Buyer, Policy Schedule) from ADNIC and uploads them to IMCRM's document management system. These documents are generated by ADNIC after policy issuance. All 3 documents must be successfully downloaded and uploaded for this step to pass.

📝 Process Flow

  1. Prerequisite Check: Validate that Step 2 (Issue Policy) completed successfully
  2. Document ID Validation: Validate that all three document IDs exist in quote:
    • Tax Invoice Document ID (insurer_tax_invoice_doc_id)
    • Tax Invoice Raised By Buyer Document ID (insurer_debit_note_doc_id)
    • Policy Schedule Document ID (insurer_policy_doc_id)
  3. Download Loop: For each document ID:
    • Build download payload with document ID using AdnicRequestBuilder::buildDownloadDocumentPayload()
    • Call ADNIC API endpoint /cyber/downloadDocument via AdnicApiService::downloadDocument()
    • Parse response and extract base64 document content
    • Decode base64 content to binary
    • Map document type to IMCRM codes (TI, CTIRBB, POLICY_SCHEDULE)
    • Upload to IMCRM using QuoteDocumentService via AdnicDocumentHandler::uploadAndAttachToQuoteDocuments()
    • Store API log for download operation
  4. Validation: Verify all three documents downloaded and uploaded successfully - all 3 must succeed
  5. Step Completion: Mark step as completed only if all 3 documents succeeded (completed_step = STEP_UPLOAD_POLICY_DOCS)

  • Download Failure: Stop on first failed download; log detailed error including document ID and API error; update insurer API status

  • Partial Success: If some documents succeed but others fail, mark step as incomplete; log which documents succeeded/failed
  • Document Type Mapping Error: Log mapping error; return error with document type details
  • API Timeout: Handle timeout per document; allow retry for failed documents only

Tax Invoice Raised By Buyer (insurer_debit_note_doc_id) → CTIRBB in IMCRM

🔄 State Management & Step Progression

The automation system maintains state throughout the process, tracking completed steps and allowing for resumable execution. This enables retry mechanisms and manual intervention when needed.

PENDING_STATUS

Initial state when automation schedule is created. Waiting to be processed by queue worker.

PROCESSING_STATUS

Automation is currently executing. Steps are being processed sequentially.

BOOKING_PENDING_STATUS

All steps completed except booking. Waiting for booking confirmation or manual intervention.

TIMEOUT_STATUS

Process timed out during execution. Eligible for retry if retry mechanism is enabled.

FAILED_STATUS

Process failed at a step. Requires manual intervention or retry after fixing issues.

📊 Completed Step Tracking

The PolicyIssuance model tracks progress using the completed_step field:

  • null - No steps completed yet
  • STEP_UPLOAD_DOCUMENTS - Step 1 completed successfully
  • STEP_ISSUE_POLICY - Steps 1 and 2 completed successfully
  • STEP_UPLOAD_POLICY_DOCS - All 3 steps completed successfully

🔄 Step Progression Logic

// Determine next step based on completed steps
getNextStep($completedStep = null): ?string
{
    return match ($completedStep) {
        null => STEP_UPLOAD_DOCUMENTS,
        STEP_UPLOAD_DOCUMENTS => STEP_ISSUE_POLICY,
        STEP_ISSUE_POLICY => STEP_UPLOAD_POLICY_DOCS,
        STEP_UPLOAD_POLICY_DOCS => null, // All steps completed
        default => STEP_UPLOAD_DOCUMENTS,
    };
}

🔄 Resumable Execution

The automation can resume from the last completed step:

  • If Step 1 fails, retry starts from Step 1
  • If Step 2 fails, retry starts from Step 2 (Step 1 already completed)
  • If Step 3 fails, retry starts from Step 3 (Steps 1 and 2 already completed)

This prevents redundant API calls and ensures efficient retry mechanisms.
