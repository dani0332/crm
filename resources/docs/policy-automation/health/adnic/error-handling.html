🛡️ Error Handling Strategy

Comprehensive Error Handling, Recovery Strategies, and Troubleshooting Guide

1. Error Handling Strategy Overview

The ADNIC automation implements a multi-layer error handling strategy with validation, logging, recovery, and retry mechanisms. This ensures robust error detection, clear error messages, and automatic recovery where possible.

Layer 1: Pre-validation

Catch errors before API calls via AdnicValidationService to prevent unnecessary API requests and provide immediate feedback.

Layer 2: API Response

Parse and handle ADNIC API errors via AdnicResponseHandler to extract meaningful error messages from API responses.

Layer 3: HTTP Errors

Handle connection, timeout, and HTTP status code errors via AdnicHttpClient with configurable timeouts and retry logic.

Layer 4: Exception Handling

Comprehensive try-catch blocks with detailed logging and graceful degradation for unexpected errors.

Layer 5: Retry Mechanism

Queue-based retry for transient failures with exponential backoff and maximum retry limits.

Layer 6: Status Updates

Automatic status updates on failure with detailed error messages stored for troubleshooting.

Key Principles:
  • Fail Fast: Validate data before making API calls
  • Fail Clearly: Provide specific, actionable error messages
  • Fail Gracefully: Update status and log errors without crashing
  • Recover Automatically: Retry transient failures automatically
  • Audit Everything: Log all errors with full context for debugging

2. Pre-validation Before API Calls

Pre-validation prevents unnecessary API calls by catching data issues early. All validation happens in AdnicValidationService before any API communication.

Validation Service Structure

declare(strict_types=1); namespace App\Services\PolicyIssuanceAutomation\Health\Adnic; class AdnicValidationService { /** * Validate required data before Issue Policy API call */ public function validateRequiredData(PersonalQuote $quote): array { // Check customer details if (!$quote->customer || !$quote->customer->name) { return $this->buildErrorResponse('Customer name is required'); } // Check nationality if (!$quote->customer->nationality) { return $this->buildErrorResponse('Customer nationality is required'); } // Check date of birth if (!$quote->customer->date_of_birth) { return $this->buildErrorResponse('Customer date of birth is required'); } // Check plan/product details if (!$quote->product || !$quote->product->name) { return $this->buildErrorResponse('Product/plan details are required'); } // Check payment information if (!$quote->payment || !$quote->payment->amount) { return $this->buildErrorResponse('Payment information is required'); } return $this->buildSuccessResponse(); } /** * Validate documents before Upload Documents API call */ public function validateDocuments(PersonalQuote $quote): array { // Check insurer quote number exists if (!$quote->insurer_quote_number) { return $this->buildErrorResponse('Insurer quote number is required'); 3. API Error Handling Patterns

API errors are handled through AdnicResponseHandler which normalizes different error formats into a consistent structure.

ADNIC API Error Response Format

{ "Success": false, "Message": "Policy generation failed", "Errors": [ "Invalid Emirates ID format", "Date of birth mismatch with Emirates ID" ], "ErrorCode": "VALIDATION_ERROR", "Data": null }

Error Detection Logic

namespace App\Services\PolicyIssuanceAutomation\Health\Adnic; class AdnicResponseHandler { /** * Check if API response contains errors */ public function hasApiErrors(array $responseBody): bool { // Check Success flag if (isset($responseBody['Success']) && $responseBody['Success'] === false) { return true; } // Check for Errors array if (!empty($responseBody['Errors'])) { return true; } // Check for error message if (isset($responseBody['Message']) && stripos($responseBody['Message'], 'error') !== false) { return true; } return false; } /** * Extract error message from API response */ public function extractErrorMessage(array $responseBody): string { $errors = $responseBody['Errors'] ?? []; if (!empty($errors)) { return implode(', ', $errors); } return $responseBody['Message'] ?? AdnicEnum::UNKNOWN_ERROR; } /** * Parse HTTP response to standard format */ public function parseHttpResponse( Response $httpResponse, string $step ): array { $statusCode = $httpResponse->status(); $responseBody = $httpResponse->json() ?? []; // Check for HTTP errors if (!$httpResponse->successful()) { return $this->buildErrorResponse( "HTTP {$statusCode}: " . ($responseBody['Message'] ?? 'Request failed'), $step, $responseBody ); } // Check for API-level errors if ($this->hasApiErrors($responseBody)) { return $this->buildErrorResponse( $this->extractErrorMessage($responseBody), $step, $responseBody ); } return $this->buildSuccessResponse($step, $responseBody); } /** * Build error response structure */ private function buildErrorResponse( string $errorMessage, string $step, array $responseData = null ): array { return [ 'status' => false, 'completed_step' => null, 'message' => "Step {$step} failed: {$errorMessage}", 'error' => $errorMessage, 'data' => $responseData ]; } /** * Build success response structure */ private function buildSuccessResponse( string $step, array $responseData ): array { return [ 'status' => true, 'completed_step' => $step, 'message' => "Step {$step} completed successfully", 'error' => null, 'data' => $responseData ]; } }

4. Exception Handling with Try-Catch Blocks

All automation steps are wrapped in try-catch blocks to handle unexpected exceptions gracefully.

Standard Exception Handling Pattern

namespace App\Services\PolicyIssuanceAutomation\Health\Adnic; class AdnicStepExecutor { public function executeStep( PolicyIssuance $process, string $step ): array { // Initialize response $response = [ 'status' => false, 'completed_step' => null, 'message' => '', 'error' => null, 'data' => null ]; try { LoggerService::info("Starting step: {$step}", extra: [ 'process_id' => $process->id, 'quote_id' => $process->quote_id, 'step' => $step ]); // Get step handler method $handlerMethod = $this->stepHandlers[$step] ?? null; if (!$handlerMethod || !method_exists($this, $handlerMethod)) { throw new \Exception("Unknown step: {$step}"); } // Execute step handler $stepResponse = $this->{$handlerMethod}($process); // Check if step succeeded if (!($stepResponse['status'] ?? false)) { LoggerService::error("Step failed: {$step}", extra: [ 'process_id' => $process->id, 'step' => $step, 'error' => $stepResponse['error'] ?? 'Unknown error' ]); // Update process status $this->updateProcessOnFailure($process, $step, $stepResponse['error']); return $stepResponse; } // Update completed step if (isset($stepResponse['completed_step'])) { $process->update(['completed_step' => $stepResponse['completed_step']]); $process->refresh(); } LoggerService::info("Step completed: {$step}", extra: [ 'process_id' => $process->id, 'completed_step' => $stepResponse['completed_step'] ?? null ]); return $stepResponse; } catch (\Illuminate\Http\Client\ConnectionException $e) { // Handle connection errors LoggerService::error('Connection exception', extra: [ 'process_id' => $process->id, 'step' => $step, 'error' => $e->getMessage() ], exception: $e); $response['error'] = 'Connection failed: ' . $e->getMessage(); $response['message'] = "Step {$step} failed due to connection error"; $this->updateProcessOnFailure($process, $step, $response['error']); return $response; } catch (\Illuminate\Http\Client\RequestException $e) { // Handle HTTP request errors LoggerService::error('HTTP request exception', extra: [ 'process_id' => $process->id, 'step' => $step, 'status_code' => $e->response?->status(), 'error' => $e->getMessage() ], exception: $e); $response['error'] = 'HTTP error: ' . $e->getMessage(); $response['message'] = "Step {$step} failed due to HTTP error"; $this->updateProcessOnFailure($process, $step, $response['error']); return $response; } catch (\Exception $e) { // Handle all other exceptions LoggerService::error('Unexpected exception', extra: [ 'process_id' => $process->id, 'step' => $step, 'error' => $e->getMessage(), 'file' => $e->getFile(), 'line' => $e->getLine() ], exception: $e); $response['error'] = 'Unexpected error: ' . $e->getMessage(); $response['message'] = "Step {$step} failed due to unexpected error"; $this->updateProcessOnFailure($process, $step, $response['error']); return $response; } } /** * Update process status on failure */ private function updateProcessOnFailure( PolicyIssuance $process, string $step, string $errorMessage ): void { $process->update([ 'status' => PolicyIssuanceEnum::FAILED_STATUS, 'insurer_api_status' => 'Failed', 'last_error_message' => $errorMessage, 'last_error_at' => now(), 'failed_attempts' => ($process->failed_attempts ?? 0) + 1 ]); } }

5. Timeout Handling and Retry Mechanisms

Timeout handling is configurable via ApplicationStorage, and retry mechanisms are implemented at both the HTTP client and queue job levels.

Timeout Configuration

namespace App\Services\PolicyIssuanceAutomation\Health\Adnic; class AdnicHttpClient { private int $apiTimeout; public function __construct() { // Get timeout from ApplicationStorage (runtime configurable) $this->apiTimeout = (int) app(ApplicationStorageService::class) ->getValueByKey( ApplicationStorageEnums::ADNIC_HEALTH_AUTOMATION_API_TIMEOUT ) ?? 30; // Default 30 seconds LoggerService::info('HTTP client initialized', extra: [ 'timeout' => $this->apiTimeout ]); } /** * Make POST request with timeout handling */ public function post( string $endPoint, array $payload = [], array $headers = [] ): Response { $fullUrl = $this->baseUrl . $endPoint; try { $response = Http::timeout($this->apiTimeout) ->withHeaders($this->mergeHeaders($headers)) ->post($fullUrl, $payload); return $response; } catch (\Illuminate\Http\Client\ConnectionException $e) { // Connection timeout or network error LoggerService::error('HTTP connection timeout', extra: [ 'endpoint' => $fullUrl, 'timeout' => $this->apiTimeout, 'error' => $e->getMessage() ]); throw $e; } catch (\Illuminate\Http\Client\RequestException $e) { // Request timeout if ($e->response && $e->response->status() === 408) { LoggerService::error('HTTP request timeout', extra: [ 'endpoint' => $fullUrl, 'timeout' => $this->apiTimeout ]); } throw $e; } } }

Queue-Based Retry Mechanism

namespace App\Jobs; use Illuminate\Bus\Queueable; use Illuminate\Contracts\Queue\ShouldQueue; use Illuminate\Foundation\Bus\Dispatchable; use Illuminate\Queue\InteractsWithQueue; use Illuminate\Queue\SerializesModels; class PolicyIssuanceJob implements ShouldQueue { use Dispatchable, InteractsWithQueue, Queueable, SerializesModels; public $connection = 'redis'; public $queue = 'policy-issuance-automation'; // Retry configuration public $tries = 3; // Maximum 3 attempts public $backoff = [60, 300]; // 1 min, 5 min delays between retries public $timeout = 600; // 10 minutes job timeout public $maxExceptions = 3; // Max exceptions before failing public function __construct( public int $policyIssuanceId ) {} /** * Execute the job */ public function handle(): void { $process = PolicyIssuance::findOrFail($this->policyIssuanceId); // Check if retry is enabled for timeout $retryEnabled = app(ApplicationStorageService::class) ->getValueByKey( ApplicationStorageEnums::ENABLE_RETRY_TIMEOUT_ADNIC_HEALTH_POLICY_ISSUANCE ); // Handle timeout status retry if ($process->status === PolicyIssuanceEnum::TIMEOUT_STATUS && $retryEnabled) { LoggerService::info('Retrying timeout process', extra: [ 'process_id' => $process->id, 'attempt' => $this->attempts() ]); // Reset status to processing $process->update(['status' => PolicyIssuanceEnum::PROCESSING_STATUS]); } // Get appropriate service and execute steps $service = app(PolicyIssuanceService::class)->init( $process->quote->quote_type, $process->quote->insurer->code ); if (!$service) { throw new \Exception("Service not found for quote type and insurer"); } $service->executeSteps($process); } /** * Handle job failure */ public function failed(\Throwable $exception): void { $process = PolicyIssuance::find($this->policyIssuanceId); if ($process) { LoggerService::error('PolicyIssuanceJob failed permanently', extra: [ 'process_id' => $process->id, 'attempts' => $this->attempts(), 'exception' => $exception->getMessage(), 'trace' => $exception->getTraceAsString() ]); // Update process to failed status $process->update([ 'status' => PolicyIssuanceEnum::FAILED_STATUS, 'insurer_api_status' => 'Failed', 'last_error_message' => $exception->getMessage(), 'last_error_at' => now() ]); // Send notification to support team // NotificationService::sendFailureAlert($process); } } /** * Calculate backoff delay for retries */ public function backoff(): array { return [60, 300]; // 1 minute, then 5 minutes } }

Process Status Updates

namespace App\Services\PolicyIssuanceAutomation; class PolicyIssuanceService { /** * Update API issuance and insurer status on failure */ public function updateAPIIssuanceAndInsurerStatus( PersonalQuote $quote, string $quoteType, int $failedStatusId, int $automationStatusId, string $stepName ): void { // Update quote insurer API status $quote->update([ 'insurer_api_status' => $failedStatusId ]); // Update automation process status $process = PolicyIssuance::where('quote_id', $quote->id) ->where('status', PolicyIssuanceEnum::PROCESSING_STATUS) ->first(); if ($process) { $process->update([ 'status' => PolicyIssuanceEnum::FAILED_STATUS, 'insurer_api_status' => 'Failed', 'last_error_message' => "Step {$stepName} failed", 'last_error_at' => now(), 'failed_attempts' => ($process->failed_attempts ?? 0) + 1 ]); } LoggerService::error('Status updated on failure', extra: [ 'quote_id' => $quote->id, 'step' => $stepName, 'status' => PolicyIssuanceEnum::FAILED_STATUS ]); } /** * Update process status on timeout */ public function updateProcessOnTimeout( PolicyIssuance $process, string $step ): void { $process->update([ 'status' => PolicyIssuanceEnum::TIMEOUT_STATUS, 'insurer_api_status' => 'Timeout', 'last_error_message' => "Step {$step} timed out", 'last_error_at' => now(), 'timeout_count' => ($process->timeout_count ?? 0) + 1 ]); LoggerService::warning('Process timed out', extra: [ 'process_id' => $process->id, 'step' => $step, 'timeout_count' => $process->timeout_count ]); } }

9. Common Error Scenarios and Solutions

Common error scenarios encountered in production and their recommended solutions.

Scenario 1: Missing Emirates ID Document

Error: "Emirates ID document is required"

Cause: Customer has not uploaded Emirates ID document

Solution:

  1. Check quote documents in UI
  2. Upload Emirates ID document (type: HEA_EID)
  3. Retry automation or manually trigger Upload Documents step

Scenario 2: API Timeout

Error: "Connection timeout after 30 seconds"

Cause: ADNIC API is slow or network issues

Solution:

  1. Check ADNIC API status
  2. Increase timeout via ApplicationStorage if persistent
  3. Wait for automatic retry (if enabled)
  4. Manually retry from last completed step

Scenario 3: Invalid Date Format

Error: "Date of birth mismatch with Emirates ID"

Cause: Date format inconsistency or incorrect date

Solution:

  1. Verify customer date of birth in quote
  2. Check Emirates ID date format
  3. Update date to match ADNIC expected format (YYYY-MM-DD)
  4. Retry Issue Policy step

Scenario 4: Duplicate Policy

Error: "Policy already exists for this quote"

Cause: Previous successful API call created policy

Solution:

  1. Check if policy number already exists in quote
  2. If policy exists, skip Issue Policy step
  3. Continue with next step (Upload Documents)
  4. Update completed_step manually if needed

Scenario 5: Document Upload Failure

Error: "Document upload failed: Invalid MIME type"

Cause: Document format not supported (must be PDF, JPEG, or PNG)

Solution:

  1. Verify document format
  2. Convert to supported format if needed
  3. Re-upload document
  4. Retry Upload Documents step

11. Troubleshooting Guide for Common Issues

Step-by-step troubleshooting guide for common issues encountered in production.

Issue 1: Automation Not Starting

Symptoms:

  • PolicyIssuance record created but status remains PENDING
  • No logs appearing for automation
  • Job not executing

Troubleshooting Steps:

  1. Check Feature Toggle:
    $enabled = app(ApplicationStorageService::class) ->getValueByKey( ApplicationStorageEnums::ENABLE_ADNIC_HEALTH_POLICY_ISSUANCE ); // Should return true
  2. Check Queue Worker:
    php artisan queue:work redis --queue=policy-issuance-automation // Should be running
  3. Check Job Status:
    // Check failed_jobs table SELECT * FROM failed_jobs WHERE queue = 'policy-issuance-automation';
  4. Manually Dispatch Job:
    PolicyIssuanceJob::dispatch($processId) ->onQueue('policy-issuance-automation');

Symptoms:

  • Same step fails multiple times
  • Error message doesn't change
  • Failed attempts count increasing

  4. Test API Manually:
    // Use tinker to test API call php artisan tinker $service = app(AdnicApiService::class); $response = $service->issuePolicy($quote);

12. Best Practices for Error Handling

Best practices and guidelines for implementing robust error handling in the automation system.

DO's ✅

  • Always validate before API calls: Use AdnicValidationService to catch errors early
  • Use consistent response structure: Always return the standard response format
  • Log comprehensively: Include process_id, quote_id, step, and error details
  • Update status on failure: Always update process status and error fields
  • Store API logs: Store every API call (success and failure) for audit
  • Handle exceptions gracefully: Wrap all API calls in try-catch blocks
  • Provide clear error messages: Use user-friendly messages with technical details
  • Enable retry for transient errors: Use timeout status for retry-eligible errors
  • Resume from last step: Don't restart from beginning on retry
  • Test error scenarios: Write tests for all error paths

DON'Ts ❌

  • Don't skip validation: Always validate before making API calls
  • Don't ignore errors: Always handle and log errors
  • Don't retry validation errors: Only retry transient failures
  • Don't log sensitive data: Never log API tokens or passwords
  • Don't crash on errors: Always return error response instead of throwing
  • Don't hardcode error messages: Use constants or configurable messages
  • Don't forget status updates: Always update process status on failure
  • Don't retry indefinitely: Set maximum retry attempts
  • Don't skip API logs: Always store API call logs
  • Don't expose internal errors: Sanitize error messages for users
