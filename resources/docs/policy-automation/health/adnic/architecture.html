📋 Overview

The Policy Issuance Automation system is a comprehensive, modular architecture designed to automate the complete policy issuance workflow with insurance providers. It provides a standardized interface for integrating multiple insurers across different Lines of Business (LOB) - Car, Health, and Travel.

Core Purpose

  • Automate the entire policy issuance lifecycle from quote to booked policy
  • Provide consistent error handling, logging, and retry mechanisms
  • Enable seamless integration with multiple insurance providers through a common interface
  • Maintain data integrity and audit trails throughout the automation process

Key Features

Multi-step automation: Sequential step execution with state management
Provider-agnostic design: Common interface for all insurance providers
Comprehensive logging: Detailed audit trails using LoggerService
Validation at each step: Pre-validation before API calls
Retry mechanisms: Handles timeouts and transient failures
Document management: Automated document upload/download and storage
Status tracking: Real-time tracking of automation progress
Queue-based processing: Asynchronous job processing for scalability

🏛️ Architecture Layers

1. Interface Layer

PolicyIssuanceInterface ├── executeSteps($process) └── createPolicyIssuanceSchedule($quote, $insurer)

Purpose: Defines the contract that all insurance provider services must implement.

Implementation: Each insurance provider (Adnic, GIG, Liva, Qatar) implements this interface.

2. Service Layer Architecture

PolicyIssuanceAutomation/ ├── PolicyIssuanceService # Core orchestration service ├── Health/ │ └── Adnic/ │ ├── AdnicInsuranceService # Main orchestrator (implements Interface) │ ├── AdnicStepExecutor # Step execution logic │ ├── AdnicApiService # API communication layer │ ├── AdnicBookPolicyService # Booking process handler │ ├── AdnicValidationService # Data validation │ ├── AdnicQuoteUpdaterService # Quote/Payment updates │ ├── AdnicDocumentHandler # Document operations │ ├── AdnicHttpClient # HTTP client │ ├── AdnicRequestBuilder # Payload builder │ └── AdnicResponseHandler # Response parser ├── Car/ │ ├── GIGInsuranceService │ └── LivaInsuranceService └── Travel/ └── QatarInsuranceService

🔧 Core Components (Adnic Health Example)

1. AdnicInsuranceService Main Orchestrator

Responsibility:
  • Implements PolicyIssuanceInterface
  • Manages the overall automation flow
  • Coordinates between different services
  • Tracks step progression
  • Handles automation enablement checks

Key Methods:

  • createPolicyIssuanceSchedule() - Initiates automation schedule
  • executeSteps() - Main entry point for step execution
  • executeStepSequence() - Sequential step execution with state management
  • getNextStep() - Determines next step based on completed steps
  • isPolicyIssuanceAutomationEnabled() - Feature toggle check
  • getStepsLockingStatus() - UI locking status for manual intervention

Pattern: Strategy Pattern Chain of Responsibility

2. AdnicStepExecutor Step Execution Layer

Responsibility:
  • Executes individual automation steps
  • Delegates to appropriate service methods
  • Updates automation status after each step
  • Handles step-specific error scenarios

Step Handlers:

private array $stepHandlers = [ AdnicEnum::STEP_UPLOAD_DOCUMENTS => 'executeUploadDocumentsStep', AdnicEnum::STEP_ISSUE_POLICY => 'executeIssuePolicyStep', AdnicEnum::STEP_UPLOAD_POLICY_DOCS => 'executeUploadPolicyDocumentsStep', ];

Note: STEP_BOOK_POLICY constant exists but is not used in automation flow. Booking is handled separately outside automation.

Pattern: Command Pattern

3. AdnicApiService API Communication Layer

Responsibility:
  • Direct interaction with insurance provider APIs
  • Orchestrates API calls with proper payloads and headers
  • Stores API logs for audit trails
  • Updates quote and payment data after successful API calls

Key Methods:

  • issuePolicy() - Creates policy with insurer
  • uploadDocuments() - Uploads customer documents to insurer
  • uploadPolicyDocumentsToIMCRM() - Downloads insurer docs and uploads to IMCRM

Dependencies: RequestBuilder, ResponseHandler, DocumentHandler, QuoteUpdater

4. AdnicHttpClient HTTP Layer

Responsibility:
  • Manages HTTP communication with insurance provider
  • Configures authentication, headers, and timeouts
  • Provides consistent error handling for HTTP errors
  • Centralizes API configuration

Configuration:

  • Base URL from config
  • Authorization token and subscription key
  • Configurable timeout from ApplicationStorage
  • Standard headers (Content-Type, Accept, Auth headers)

Pattern: Facade Pattern for HTTP client

5. AdnicRequestBuilder Payload Builder

Responsibility:
  • Constructs API request payloads from domain models
  • Formats dates, addresses, and other data as per API requirements
  • Builds headers for specific API calls
  • Encapsulates payload structure knowledge

Key Methods:

  • buildIssuePolicyPayload() - Policy creation payload
  • buildUploadDocumentsPayload() - Document upload payload
  • buildDownloadDocumentPayload() - Document download payload
  • buildIssuePolicyHeaders() - Custom headers for policy issuance

Pattern: Builder Pattern

6. AdnicResponseHandler Response Parser

Responsibility:
  • Normalizes API responses into consistent structure
  • Parses success/error responses
  • Builds standardized step response arrays
  • Handles HTTP status codes and API-specific error formats

Response Structure:

[ 'status' => bool, // Success/failure 'completed_step' => string, // Last completed step 'message' => string, // User-friendly message 'error' => mixed, // Error details 'data' => mixed, // Response data ]

Key Methods:

  • parseHttpResponse() - Parse HTTP response to standard format
  • buildStepResponse() - Build consistent step response
  • hasApiErrors() - Check for API-level errors
  • extractErrorMessage() - Extract error messages

Pattern: Adapter Pattern

7. AdnicValidationService Validation Layer

Responsibility:
  • Pre-validates data before API calls
  • Validates quote data completeness
  • Validates document availability
  • Validates booking prerequisites
  • Prevents unnecessary API calls with invalid data

Validation Types:

  • Required Data Validation: Customer, payment, plan details
  • Document Validation: Emirates ID, required documents
  • Download Documents Validation: Document IDs availability
  • Book Policy Validation: Booking details completeness

Pattern: Validator Pattern

8. AdnicBookPolicyService Booking Process

Responsibility:
  • Manages final booking process
  • Updates booking details
  • Triggers Sage process integration
  • Manages UI step locking status
  • Determines editable steps based on automation state

Key Methods:

  • bookPolicy() - Execute complete booking process
  • updateBookingDetails() - Update payment and commission details
  • getStepsLockingStatus() - Determine UI editability

Integration Points:

  • CentralService for booking updates
  • SageApiService for booking to Sage
  • BookPolicyRequest validation

9. AdnicQuoteUpdaterService Data Updater

Responsibility:
  • Updates quote data from API responses
  • Updates payment and commission information
  • Maintains data consistency between systems
  • Updates policy numbers, dates, and amounts

Key Methods:

  • updateQuoteFromIssuePolicyResponse() - Updates quote with policy details
  • updatePaymentFromIssuePolicyResponse() - Updates payment with commission

Updates:

  • Policy number, dates, amounts
  • VAT and commission details
  • Document IDs from insurer
  • Quote status transitions

10. AdnicDocumentHandler Document Management

Responsibility:
  • Fetches documents from Azure storage
  • Validates document types and formats
  • Uploads documents to insurer and IMCRM
  • Maps document types between systems
  • Handles base64 encoding/decoding

Key Features:

  • Document type mapping (HEA_EID → insurer codes)
  • MIME type validation (PDF, JPEG, PNG)
  • Azure storage integration
  • Document content validation

Methods:

  • fetchDocumentContent() - Retrieve from Azure
  • uploadAndAttachToQuoteDocuments() - Upload to IMCRM
  • getDocumentByType() - Find documents by type
  • getDocTypeCodeForHealth() - Map to insurer codes
  • getDocTypeCodeForIMCRM() - Map to IMCRM codes

🎨 Design Patterns & Principles

1. Single Responsibility Principle (SRP)

Each service has a single, well-defined responsibility:

Service Responsibility
HttpClient HTTP communication only
RequestBuilder Payload construction only
ResponseHandler Response parsing only
ValidationService Data validation only
DocumentHandler Document operations only

2. Dependency Injection

All services use constructor injection for dependencies:

public function __construct( private AdnicStepExecutor $stepExecutor, private AdnicValidationService $validationService, private AdnicBookPolicyService $bookPolicyService, private AdnicResponseHandler $responseHandler, ) {}

3. Interface Segregation

PolicyIssuanceInterface defines minimal required methods:

  • executeSteps($process)
  • createPolicyIssuanceSchedule($quote, $insurer)

4. Chain of Responsibility

Step execution flows through a chain:

AdnicInsuranceService → AdnicStepExecutor → AdnicApiService → AdnicHttpClient

5. Strategy Pattern

Different insurance providers implement the same interface with provider-specific strategies.

6. Builder Pattern

AdnicRequestBuilder constructs complex payloads step-by-step.

7. Facade Pattern

AdnicHttpFacade provides a simplified interface to the HTTP client.

8. Adapter Pattern

AdnicResponseHandler adapts various API response formats to a consistent structure.

9. Factory Pattern

PolicyIssuanceService::init() creates appropriate service instance based on quote type and insurer.

📝 Key Implementation Guidelines

1. Strict Typing

ALWAYS use strict typing in all automation files:
declare(strict_types=1);

2. Comprehensive Logging

Log at every significant step:

LoggerService::startQuoteLogging($quote, LoggerFeatureEnum::ADNIC_HEALTH_POLICY_AUTOMATION); LoggerService::info('Step description', extra: [ 'process_id' => $process->id, 'step' => $currentStep, // ... relevant context ]);

Log Types:

  • info() - Successful operations, step completion
  • error() - Failures, exceptions
  • warning() - Automation disabled, configuration issues

3. Consistent Response Structure

All methods return standardized response:

return [ 'status' => bool, // true = success, false = failure 'completed_step' => string, // Step identifier 'message' => string, // User-friendly message 'error' => mixed, // Error details (null on success) 'data' => mixed, // Response data (null on failure) ];

4. Pre-Validation Before API Calls

Always validate data before making API calls:

$validationResult = $this->validationService->validateRequiredData($quote); if (!$validationResult['status']) { return $validationResult; }
Benefits:
  • Prevents unnecessary API calls
  • Provides clear error messages
  • Saves API costs
  • Improves user experience

5. API Log Storage

Store every API call for audit trails:

app(PolicyIssuanceService::class)->storePolicyIssuanceLog( $quote, $payload, // Request payload $response, // Response data $endpoint, // Full URL $step, // Step identifier $status, // SUCCESS_STATUS or FAILED_STATUS $process // PolicyIssuance model );

6. Step Progression Management

Update completed step after each success:

if (($response['status'] ?? false) && isset($response['completed_step'])) { $process->update(['completed_step' => $response['completed_step']]); $process->refresh(); }

7. Error Handling Strategy

Exception Handling:

try { // Step execution } catch (Exception $e) { $response['error'] = $e->getMessage(); LoggerService::error('Exception occurred', extra: [ 'process_id' => $process->id, ], exception: $e); return $response; }

8. HTTP Client Configuration

Centralize API configuration:

private string $baseUrl; // From config private array $authParam; // Authorization credentials private array $baseHeaders; // Standard headers private int $apiTimeout; // From ApplicationStorage

9. Document Handling

Document Flow:

1. Fetch

Azure Storage → Application

2. Validate

MIME type, content

3. Transform

Base64 encoding

4. Upload

Application → Insurer or IMCRM

5. Map

Document type codes between systems

10. State Management

Process States (in PolicyIssuance model):

  • PENDING_STATUS - Waiting to be processed
  • PROCESSING_STATUS - Currently being processed
  • BOOKING_PENDING_STATUS - Waiting for booking
  • TIMEOUT_STATUS - Timed out, eligible for retry
  • FAILED_STATUS - Failed, manual intervention required

Completed Steps (in completed_step field):

  • null - No steps completed
  • STEP_UPLOAD_DOCUMENTS - Documents uploaded (per-member)
  • STEP_ISSUE_POLICY - Policy created (with pre-captured payment)
  • STEP_UPLOAD_POLICY_DOCS - All 3 policy docs retrieved and uploaded

Note: STEP_BOOK_POLICY is not part of automation flow. Booking is handled separately.

11. Feature Toggle Pattern

Always check if automation is enabled:

public function isPolicyIssuanceAutomationEnabled(): bool { return app(ApplicationStorageService::class) ->getValueByKey(ApplicationStorageEnums::ENABLE_ADNIC_HEALTH_POLICY_ISSUANCE); }

✅ Best Practices Summary

DO:

  • ✅ Always use strict typing (declare(strict_types=1))
  • ✅ Log comprehensively at every step
  • ✅ Validate data before API calls
  • ✅ Use dependency injection
  • ✅ Return consistent response structure
  • ✅ Store API logs for audit
  • ✅ Update step progression after each success
  • ✅ Handle exceptions gracefully
  • ✅ Use feature toggles for runtime control
  • ✅ Implement retry mechanisms
  • ✅ Follow Single Responsibility Principle
  • ✅ Use meaningful variable and method names
  • ✅ Add inline documentation
  • ✅ Test thoroughly (unit, integration, feature)

DON'T:

  • ❌ Skip validation steps
  • ❌ Make API calls without logging
  • ❌ Hardcode configuration values
  • ❌ Ignore error responses
  • ❌ Update status without validation
  • ❌ Skip dependency injection
  • ❌ Return inconsistent response structures
  • ❌ Log sensitive data
  • ❌ Couple services tightly
  • ❌ Skip exception handling
  • ❌ Ignore timeout configurations
  • ❌ Deploy without testing
