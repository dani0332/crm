📋 Overview

The Alliance Travel Policy Issuance Automation system is a comprehensive, modular architecture designed to automate the complete policy issuance workflow with Alliance Insurance Company. It provides a standardized interface for integrating with Alliance's travel insurance APIs across different travel types (Inbound and Outbound).

Core Purpose

  • Automate the entire travel policy issuance lifecycle from quote finalization to booked policy
  • Provide consistent error handling, logging, and retry mechanisms
  • Enable seamless integration with Alliance Insurance through a common interface
  • Maintain data integrity and audit trails throughout the automation process
  • Support both Inbound and Outbound travel policies with appropriate handling

Key Features

Multi-step automation: Sequential step execution with state management
Provider-agnostic design: Common interface for all insurance providers
Comprehensive logging: Detailed audit trails using LoggerService
Retry mechanisms: Handles document generation delays with configurable retries
Document management: Automated document download, upload, and storage
Status tracking: Real-time tracking of automation progress

HTTP Client Integration API Communication

Responsibility:
  • Manages HTTP communication with Alliance API
  • Configures authentication via agency_id and agency_code
  • Provides consistent error handling for HTTP errors
  • Centralizes API configuration

Configuration:

  • Base URL from config: ALLIANCE_API_BASE_URL
  • Authentication parameters: agency_id and agency_code
  • Timeout: 20 seconds (configurable)
  • Standard headers: Content-Type: application/json

Method:

private function allianceHttpCall($endPoint, $param) { $headers = ['Content-Type' => 'application/json']; $payload = array_merge($this->authParam, $param); $url = $this->baseUrl . $endPoint; return Http::timeout(20)->withHeaders($headers)->post($url, $payload); }

Document Mapping:

  • Certificate of Insurance → TRAVEL_POLICY_SCHEDULE

Payment & Commission Management Financial Operations

Responsibility:
  • Payment is PRE-CAPTURED before automation starts
  • Transaction ID extracted from $payment->paymentSplits->first()?->paymentCharges?->transaction_id
  • Transaction ID used as agency_reference in PurchasePolicy step
  • Updates payment records with commission details from buyer tax invoice
  • Calculates VAT and commission percentages
  • Updates commission schedules via SplitPaymentService
  • Manages insurer tax invoice numbers

Payment Flow:

  • Payment already authorized/captured before automation
  • Transaction ID used for reference only in PurchasePolicy API call

Commission Updates:

  • Commission details fetched from buyer tax invoice API
  • Commission amount (including/excluding VAT)
  • Commission percentage calculation
  • Insurer tax invoice number
  • Invoice date and description
  • Commission schedule updated via SplitPaymentService->updateCommissionSchedule()

Travel Type Management Travel-Specific Logic

Responsibility:
  • Determines travel type (Inbound/Outbound) from quote
  • Calculates policy expiry dates based on travel type
  • Handles multi-trip coverage with special rules
  • Manages cover days calculation

Travel Types:

  • Inbound: Travelers coming to UAE
  • Outbound: UAE residents traveling abroad

Special Handling:

  • Multi-trip Inbound policies: Fixed 180 days cover (maximum, regardless of days_cover_for)
  • Other travel types: Cover days based on days_cover_for field
  • Policy expiry date calculation: Last cover day = expiry date

🎨 Design Patterns & Principles

1. Strategy Pattern

AllianceInsuranceService implements PolicyIssuanceInterface with provider-specific strategy for Travel insurance.

2. Sequential Execution Pattern

Steps execute in strict order, each dependent on the previous step's success:

IssuePolicy → PurchasePolicy → UploadPolicyDocuments → FillBookingDetails → BookPolicy

3. Retry Pattern

Document generation retry mechanism with configurable delays:

$maxRetries = 5; $retryDelay = 10; // seconds $retryCount = 0; do { sleep($retryDelay); // 10 seconds $policyDocuments = $this->allianceHttpCall($endPoint, $payload); if ($policyDocuments->failed() && str_contains($response->errors[0], 'Policy documents are still generating')) { $retryCount++; } else { break; } } while ($retryCount < $maxRetries); // Max 5 retries

4. Dependency Injection

Services use Laravel's service container for dependency resolution:

🔄 State Management

Process States

States tracked in PolicyIssuance model:

  • PENDING_STATUS - Waiting to be processed
  • PROCESSING_STATUS - Currently being processed
  • FAILED_STATUS - Failed, manual intervention required
  • COMPLETED_STATUS - All steps completed successfully

Completed Steps

Steps tracked in completed_step field:

  • null - No steps completed
  • ALLIANCE_TRAVEL_ISSUE_POLICY - Step 1 completed
  • ALLIANCE_TRAVEL_PURCHASE_POLICY - Step 2 completed
  • ALLIANCE_TRAVEL_UPLOAD_POLICY_DOCUMENTS - Step 3 completed
  • ALLIANCE_TRAVEL_FILL_POLICY_BOOKING_DETAILS - Step 4 completed
  • ALLIANCE_TRAVEL_BOOK_POLICY - Step 5 completed

Step Progression Logic

public function getNextStep($completedStep = null): ?string { $allSteps = PolicyIssuanceEnum::getPolicyIssuanceSteps( InsuranceProviderEnum::ALNC->value, self::TYPE ); if (!$completedStep) { return $allSteps[0]; // First step } $completedStepIndex = array_search($completedStep, $allSteps); if ($completedStepIndex === false || $completedStepIndex === count($allSteps) - 1) { return null; // No next step } return $allSteps[$completedStepIndex + 1]; }

✅ Best Practices Summary

DO:

  • ✅ Always log comprehensively at every step
  • ✅ Store API logs for audit trails
  • ✅ Update step progression after each success
  • ✅ Handle exceptions gracefully
  • ✅ Use feature toggles for runtime control
  • ✅ Implement retry mechanisms for transient failures
  • ✅ Validate data before API calls
  • ✅ Map documents correctly between systems

DON'T:

  • ❌ Skip logging steps
  • ❌ Hardcode configuration values
  • ❌ Ignore error responses
  • ❌ Update status without validation
  • ❌ Skip retry mechanisms for document generation
  • ❌ Log sensitive customer data
