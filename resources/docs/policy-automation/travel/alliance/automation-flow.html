🔄 Alliance Travel Automation Flow

Complete 5-Step Policy Issuance Workflow with Detailed Process Documentation

💳 Pre-Automation Payment Capture

🔑 Critical Prerequisite Step

Auto-capture is a mandatory prerequisite that executes BEFORE the automation workflow begins. Payment must be successfully captured before automation can proceed.

Payment Flow

  1. Customer pays online → Payment authorized
  2. Background job processes → CcPaymentProcess handles split payment approval
  3. Auto-capture executes → SplitPaymentService->processSplitPaymentApprove() calls CRUDService->capturePayment()
  4. Marshall API call → Creates PaymentAction record with action_type: 'CAPTURE' and amount
  5. Success path: If capture succeeds → Automation workflow scheduled via createPolicyIssuanceAutomation()
  6. Failure path: If capture fails → handleAutomationError() sets insurer_api_status_id to AUTO_CAPTURE_FAILED_STATUS_ID and allocates to team

Implementation Details

  • Code Location: SplitPaymentService.php lines 770-792, 1475-1487
  • Retry Logic: Up to 3 attempts with 1-second delay between retries
  • Provider Support: Currently implemented for Alliance Travel and other e-commerce providers
  • Failure Handling: If capture fails, automation is prevented from starting and quote is allocated for manual handling

⚠️ Important: This explains why documentation refers to "pre-captured" payments - the payment is already captured before any automation steps execute.

📋 Complete Automation Workflow Overview

The Alliance Travel Policy Issuance Automation follows a sequential 5-step process, where each step must complete successfully before proceeding to the next. The system maintains state throughout the process, allowing for retry mechanisms and manual intervention when needed.

Step 1

Issue Policy

Finalize policy with Alliance API using customer and traveller details. Updates quote with policy ID, premium, VAT, and dates.

Step 2

Purchase Policy

Purchase finalized policy and update quote with policy number and payment with tax invoice number.

Step 3

Upload Policy Documents

Retrieve policy documents from Alliance (with retry mechanism) and upload to IMCRM with automatic mapping.

Step 4

Fill Booking Details

Retrieve buyer tax invoice and update payment/commission details with automatic schedule updates.

Step 5

Book Policy

Finalize booking process with Sage ERP integration for commission processing.

💡 Workflow Characteristics

  • Sequential Execution: Steps execute in order, each dependent on the previous step's success
  • State Management: Completed steps are tracked in the PolicyIssuance model's completed_step field
  • Resumable: Failed automations can be resumed from the last completed step
  • Audit Trail: Every API call is logged in PolicyIssuanceLog for complete traceability
  • Error Recovery: Each step has specific error handling and can be retried independently
  • Retry Mechanism: Step 3 includes automatic retry for document generation delays

1️⃣ Step 1: Issue Policy

The first step finalizes the policy with Alliance Insurance Company using customer information, traveller details, and plan information. This step establishes the policy foundation and generates the policy ID.

📝 Process Flow

  1. Travel Type Determination: Determine travel type (Inbound/Outbound) based on quote's direction_code
  2. Plan Selection: Retrieve selected plan from TravelQuotePlanDetails based on payment's plan_id
  3. Customer Data Collection: Extract primary member and all travellers from customerMembers relationship
  4. Payload Construction: Build finalise payload with:
    • Quote ID and scheme ID from selected plan
    • Customer title, first name, last name (from primary member)
    • Traveller details arrays (title, first name, last name, DOB, passport, nationality)
    • Static contact details (email and mobile - privacy protection)
    • Agency reference
  5. API Call: Call Alliance API endpoint /v1/quote/{travelType}/finalise via allianceHttpCall()
  6. Response Parsing: Extract policy ID, premium amount from response
  7. VAT Calculation: Calculate VAT-applicable price and VAT amount
  8. Cover Days Calculation: Calculate cover days
    • Multi-trip Inbound: Fixed at 180 days (maximum)
    • Other types: Uses days_cover_for from quote
  9. Expiry Date Calculation: Policy expiry = policy start date + cover days - 1 day
  10. Quote Update: Update quote with policy ID, premium, VAT, price VAT applicable, policy issuance date, and policy expiry date
  11. API Log Storage: Store complete API request and response in PolicyIssuanceLog
  12. Step Completion: Mark step as completed (completed_step = ALLIANCE_TRAVEL_ISSUE_POLICY)

✅ Success Criteria

  • API returns HTTP 200 status code with successful response
  • Policy ID is generated and present in response
  • Premium amount is extracted from response
  • Quote record is updated with policy ID, premium, VAT, dates
  • Policy expiry date is calculated correctly (last cover day)
  • Step is marked as completed (completed_step = ALLIANCE_TRAVEL_ISSUE_POLICY)
  • API log is stored with SUCCESS_STATUS

❌ Failure Handling

  • API Error: Log detailed error including endpoint and payload; update insurer API status to failed; store failed log; return error response
  • HTTP Exception: Catch and log exception with full context; update process status; return error response
  • Missing Data: Validate required fields before API call; return error with specific missing field
  • Invalid Response: Validate response structure; log parsing errors; return error with specific message
  • Database Update Failure: Log database errors; maintain API success but flag update failure

🔑 Key Data Updates

  • Quote: insurer_policy_id, price_with_vat, vat, price_vat_applicable, policy_issuance_date, policy_expiry_date
  • PolicyIssuance: completed_step = ALLIANCE_TRAVEL_ISSUE_POLICY
  • PolicyIssuanceLog: Complete request/response payload, endpoint URL, status, timestamp

2️⃣ Step 2: Purchase Policy

The second step purchases the finalized policy with Alliance Insurance Company. This step generates the policy number and tax invoice number.

📝 Process Flow

  1. Prerequisite Check: Validate that Step 1 (Issue Policy) completed successfully by checking completed_step
  2. Policy ID Validation: Ensure insurer_policy_id exists from Step 1
  3. Transaction ID Extraction: Extract transaction ID from payment splits for agency reference
    • Source: $payment->paymentSplits->first()?->paymentCharges?->transaction_id
    • Note: Payment is PRE-CAPTURED before automation starts; transaction ID is used as reference only
  4. Payload Construction: Build purchase payload with:
    • Policy ID from quote
    • Agency reference (transaction ID from payment)
  5. API Call: Call Alliance API endpoint /v1/quote/{travelType}/purchase via allianceHttpCall()
  6. Response Parsing: Extract policy number and tax invoice number from response
  7. Quote Update: Update quote with policy number
  8. Payment Update: Update payment record with insurer tax invoice number
  9. API Log Storage: Store complete API request and response in PolicyIssuanceLog
  10. Step Completion: Mark step as completed (completed_step = ALLIANCE_TRAVEL_PURCHASE_POLICY)

3️⃣ Step 3: Upload Policy Documents

The third step retrieves policy documents from Alliance Insurance Company. This step includes a retry mechanism to handle document generation delays, then uploads documents to IMCRM with automatic type mapping.

📝 Process Flow

  1. Prerequisite Check: Validate that Step 2 (Purchase Policy) completed successfully
  2. Policy ID Validation: Ensure insurer_policy_id exists
  3. Retry Loop: Attempt to retrieve documents with retry mechanism:
    • Max retries: 5 attempts
    • Retry delay: 10 seconds between attempts
    • Call Alliance API endpoint /v1/policy/{travelType}/documents
    • Check if error message contains "Policy documents are still generating"
    • Retry only if "still generating" error; break on success or other errors
  4. Response Validation: Validate API response and extract policy documents array
  5. Document Processing Loop: For each policy document:
    • Map Alliance document name to IMCRM document code using getTravelDocumentMapping()
    • If mapping found, download document from URL
    • Upload to Azure Storage
    • Attach to quote documents with correct document type
    • Trigger watermarking job
  6. Quote Status Update: Update quote status to PolicyIssued
  7. API Log Storage: Store API log for document retrieval
  8. Step Completion: Mark step as completed (completed_step = ALLIANCE_TRAVEL_UPLOAD_POLICY_DOCUMENTS)

  • Upload Failure: Log Azure upload errors; return error with specific document

📄 Document Mapping

  • Policy Tax Invoice → TRAVEL_TAX_INVOICE
  • Certificate of Insurance → TRAVEL_POLICY_SCHEDULE
  • Unmapped documents are logged but do not stop the process

4️⃣ Step 4: Fill Booking Details

The fourth step retrieves the buyer tax invoice from Alliance and updates payment records with commission details, VAT information, and invoice data. This step also updates the commission schedule.

📝 Process Flow

  1. Prerequisite Check: Validate that Step 3 (Upload Policy Documents) completed successfully
  2. Policy Data Validation: Ensure insurer_policy_id and policy_number exist
  3. Payload Construction: Build buyer tax invoice payload with policy ID and policy number
  4. API Call: Call Alliance API endpoint /v1/agency/buyer-tax-invoices via allianceHttpCall()
  5. Response Parsing: Extract buyer tax invoice details from response array
  6. Document Download: Download buyer tax invoice from URL
  7. Document Upload: Upload buyer tax invoice to Azure Storage and attach to quote
  8. Date Conversion: Convert tax invoice date from "d-M-y" format to "Y-m-d"
  9. Commission Calculation: Calculate commission percentage from buyer tax invoice details
  10. Payment Update: Update payment record with commission details from buyer tax invoice:
    • Commission amount (including tax): commission
    • Commission VAT: commission_vat
    • Commission VAT applicable: commission_vat_applicable
    • Commission percentage: commmission_percentage
    • Insurer commission invoice number: insurer_commmission_invoice_number
    • Insurer invoice date: insurer_invoice_date
    • Invoice description
  11. Commission Schedule Update: Trigger SplitPaymentService->updateCommissionSchedule() to update commission schedule
  12. API Log Storage: Store API log for buyer tax invoice retrieval
  13. Step Completion: Mark step as completed (completed_step = ALLIANCE_TRAVEL_FILL_POLICY_BOOKING_DETAILS)

5️⃣ Step 5: Book Policy

The final step triggers the booking process with Sage ERP integration. This step finalizes the policy issuance automation and initiates commission processing.

📝 Process Flow

  1. Prerequisite Check: Validate that Step 4 (Fill Booking Details) completed successfully
  2. Request Object Creation: Build Sage booking request object with:
    • Quote ID
    • Model type (Travel)
    • Send policy flag (false)
    • Send policy type (SAGE)
    • Transaction payment status (null)
  3. Sage API Call: Post booking request to Sage via SageApiService::postBookPolicyToSage()
  4. Response Validation: Validate Sage API response
  5. Step Completion: Mark step as completed (completed_step = ALLIANCE_TRAVEL_BOOK_POLICY)
  6. Process Completion: Mark entire automation process as completed

🔄 State Management & Step Progression

The automation system maintains state throughout the process, tracking completed steps and allowing for resumable execution. This enables retry mechanisms and manual intervention when needed.

📊 Completed Step Tracking

The PolicyIssuance model tracks progress using the completed_step field:

  • null - No steps completed yet
  • ALLIANCE_TRAVEL_ISSUE_POLICY - Step 1 completed successfully
  • ALLIANCE_TRAVEL_PURCHASE_POLICY - Steps 1 and 2 completed successfully
  • ALLIANCE_TRAVEL_UPLOAD_POLICY_DOCUMENTS - Steps 1, 2, and 3 completed successfully
  • ALLIANCE_TRAVEL_FILL_POLICY_BOOKING_DETAILS - Steps 1, 2, 3, and 4 completed successfully
  • ALLIANCE_TRAVEL_BOOK_POLICY - All 5 steps completed successfully

🔄 Step Progression Logic

// Determine next step based on completed steps
getNextStep($completedStep = null): ?string
{
    $allSteps = PolicyIssuanceEnum::getPolicyIssuanceSteps(
        InsuranceProviderEnum::ALNC->value,
        self::TYPE
    );

    if (!$completedStep) {
        return $allSteps[0]; // First step
    }

    $completedStepIndex = array_search($completedStep, $allSteps);
    if ($completedStepIndex === false ||
        $completedStepIndex === count($allSteps) - 1) {
        return null; // No next step
    }

    return $allSteps[$completedStepIndex + 1];
}

🔄 Resumable Execution

The automation can resume from the last completed step:

  • If Step 1 fails, retry starts from Step 1
  • If Step 2 fails, retry starts from Step 2 (Step 1 already completed)
  • If Step 3 fails, retry starts from Step 3 (Steps 1 and 2 already completed)
  • If Step 4 fails, retry starts from Step 4 (Steps 1, 2, and 3 already completed)
  • If Step 5 fails, retry starts from Step 5 (Steps 1, 2, 3, and 4 already completed)

This prevents redundant API calls and ensures efficient retry mechanisms.
