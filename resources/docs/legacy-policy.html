📋 Legacy Policy & Move to IMCRM

View Insly legacy policies, assign user/email via Application Storage, and move leads into IMCRM

✓ Active Feature

❓ What is Legacy Policy?

Legacy policies are policy records stored in the Insly system (MongoDB). They represent business that existed before or outside the current IMCRM quote flow. The Legacy Policy feature allows authorised users to search and view these policies, and to Move to IMCRM—i.e. create or link an IMCRM lead (quote) so the policy can be managed inside the application.

💡 Key Concepts

Insly: External policy management system; data is stored in MongoDB (InslyDetail model).
Move to IMCRM: Either link an existing IMCRM quote by policy number or email+payment date, or create a new lead and attach the legacy policy (insly_id) to the appropriate LOB table.
Application Storage: Key-value store used to assign a user ID (advisor) and customer email to specific legacy policies when Insly data is missing (e.g. no renewer person, no customer email).

🔐 Access & Permissions

📍 Routes

  • GET /legacy-policy – List (index); search runs only when at least one filter is provided. Route name: legacy-policy.index.
  • GET /legacy-policy/{legacy_policy} – Show policy detail; {legacy_policy} is the MongoDB document _id. Route name: legacy-policy.show. Returns 404 if not found.
  • POST /legacy-policy/move-to-imcrm – Move to IMCRM (body: policy_oid, validateAll, isInertia).
  • GET /legacy-policy/{policyNumber}/policy – Look up by policy number, then redirect to show using MongoDB _id. Route name: view-legacy-policy.renewal-uploads.
  • POST /legacy-policy/get-s3-temp-url – Temporary URL for document viewing (body: legacyPolicyId, fileName).
  • POST /migrate-legacy-policy/{poid} – CAPI migration (separate flow). Route name: migrate-legacy-policy. Migrate (POID) form on Index is shown only to users with MIGRATE_INSLY_LEAD.

🔑 Permissions

  • List, show, and Move to IMCRM require one of: VIEW_LEGACY_DETAILS or VIEW_ALL_LEADS (middleware on index, show, moveToImcrm).
  • Sidebar: "Legacy Policies" link when user has VIEW_LEGACY_DETAILS or VIEW_ALL_LEADS.
  • Migrate (CAPI) form visibility: MIGRATE_INSLY_LEAD (frontend only; route itself is not permission-gated in the controller).

⚙️ Application Storage: Assign User ID and Email to Legacy Policy

Why This Exists

When you click Move to IMCRM, the system must create (or link) an IMCRM lead. Every lead needs:

  • An advisor (sales person) — the user in your system who “owns” the lead.
  • A customer email — required for validation and for the lead record.

Normally these come from Insly: the policy’s renewer/broker is matched to an InslyAdvisor to get a user_id, and the customer’s email is read from the policy. But some legacy policies in Insly have no renewer person or no customer email. In those cases, Move to IMCRM would fail with “Advisor not found” or “Customer email not found” unless we provide a fallback.

Application Storage is that fallback. It is a key-value store (e.g. in your database or admin UI) where an administrator can say: “For this specific legacy policy (identified by its policy OID), use this user ID as the advisor and/or this email as the customer email.” The Move to IMCRM logic checks these keys only when Insly did not provide the data, so you can fix one policy at a time without changing Insly data.

How It Works (In Plain Terms)

Advisor (user ID) assignment

  1. The user clicks “Move to IMCRM” for a legacy policy (e.g. policy OID 12345).
  2. The system tries to find the advisor from Insly (renewer_person or broker → InslyAdvisor → user_id).
  3. If no advisor is found, it reads from Application Storage: INSLY_TEMP_SALES_PERSON_ID and INSLY_TEMP_POLICY_OID.
  4. If the stored policy OID equals 12345, the system uses the stored user ID as the advisor for the new lead.
  5. If there is still no advisor, the request fails with 400 – Advisor not found.

Customer email assignment

  1. The system needs a customer email for the lead (validation and record creation).
  2. It first uses the email from the Insly policy (policy.customer.email).
  3. If that is empty, it reads INSLY_TEMP_CUSTOMER_EMAIL and INSLY_TEMP_CUSTOMER_POLICY_OID from Application Storage.
  4. If the stored policy OID equals the policy being moved, the stored email is used for that policy.
  5. If there is still no email, the request fails with 400 – Customer email not found.

When to Use It

  • Policy has no renewer in Insly: Set INSLY_TEMP_POLICY_OID to that policy’s OID and INSLY_TEMP_SALES_PERSON_ID to the correct advisor’s user ID (from your users table). Then run Move to IMCRM for that policy.
  • Policy has no customer email in Insly: Set INSLY_TEMP_CUSTOMER_POLICY_OID to that policy’s OID and INSLY_TEMP_CUSTOMER_EMAIL to the known customer email. Then run Move to IMCRM.
  • You can set both advisor and email for the same policy (same OID in both pairs), or use them for different policies. The two pairs work independently.

Storage Keys (ApplicationStorageEnums)

These four keys are defined in ApplicationStorageEnums and stored in the application_storage table (or your configured store). They work in pairs: one key holds the value (user ID or email), the other holds the policy OID that value applies to.

Key Purpose Used When
INSLY_TEMP_SALES_PERSON_ID User ID of the advisor/sales person to assign to the legacy lead (integer, from users.id). Move to IMCRM: advisor not found from Insly; used only when INSLY_TEMP_POLICY_OID equals the policy being moved.
INSLY_TEMP_POLICY_OID Policy OID (integer) for which the temp sales person ID applies. Must match the legacy policy’s policy_oid. Checked together with INSLY_TEMP_SALES_PERSON_ID; both must be set and OID must match.
INSLY_TEMP_CUSTOMER_EMAIL Customer email address to use when the policy has no email in Insly. Must be a valid email format. Used when policy has no customer.email and INSLY_TEMP_CUSTOMER_POLICY_OID equals this policy’s policy_oid.
INSLY_TEMP_CUSTOMER_POLICY_OID Policy OID (integer) for which the temp customer email applies. Must match the legacy policy’s policy_oid. Checked together with INSLY_TEMP_CUSTOMER_EMAIL; both must be set and OID must match.

Where It’s Used in Code (InslyDetailRepository)

The logic lives in InslyDetailRepository::fetchSaveToImcrm (and for email again in prePareData when building the lead payload). The flow is: try Insly first; if missing, read Application Storage and apply only when the stored policy OID matches the current policy.

📌 Advisor / Sales Person (fetchSaveToImcrm)

  • Step 1: Resolve advisor from Insly: policy’s renewer_person or quote.broker → lookup InslyAdvisor by name → user_id.
  • Step 2: If that is null, read INSLY_TEMP_SALES_PERSON_ID and INSLY_TEMP_POLICY_OID from Application Storage.
  • Step 3: If both are set and INSLY_TEMP_POLICY_OID == $policyID (the policy being moved), use INSLY_TEMP_SALES_PERSON_ID as advisor_id for the new lead.
  • If advisor is still null after this, Move to IMCRM returns 400 – "Advisor not found."

📌 Customer Email (fetchSaveToImcrm & prePareData)

  • Step 1: Use $policy['customer']['email'] from Insly.
  • Step 2: If email is empty, read INSLY_TEMP_CUSTOMER_EMAIL and INSLY_TEMP_CUSTOMER_POLICY_OID.
  • Step 3: If INSLY_TEMP_CUSTOMER_POLICY_OID == policy_oid, use INSLY_TEMP_CUSTOMER_EMAIL for validation and for the new lead.
  • The same fallback is applied again in prePareData() when building the payload so the created lead gets the correct email.
  • If email is still empty, Move to IMCRM returns 400 – "Customer email not found."

Example: Moving One Policy With Missing Data

Legacy policy OID 98765 has no renewer in Insly and no customer email. You want to assign advisor user ID 42 and use customer@example.com as the customer email.

  1. In Application Storage (admin UI or database), set:
    • INSLY_TEMP_SALES_PERSON_ID = 42
    • INSLY_TEMP_POLICY_OID = 98765
    • INSLY_TEMP_CUSTOMER_EMAIL = customer@example.com
    • INSLY_TEMP_CUSTOMER_POLICY_OID = 98765
  2. Open the Legacy Policy detail page for that policy and click Move to IMCRM.
  3. The system will use user 42 as advisor and customer@example.com as email for that policy only. Other policies are unaffected.
  4. After a successful move, you can change the stored OIDs/values for the next policy if needed (the keys are effectively “one policy at a time” by design).

Seeding and Updating Values (ApplicationStorageSeeder)

The seeder method seedLegacyPolicyKeys() creates the four keys in application_storage with placeholder values (e.g. 1 or a date). These placeholders are not valid for a real move—an administrator must update them to the actual policy OID, user ID, and/or email for the legacy policy they are moving. Updates are done through your Application Storage admin interface or by updating the application_storage table (e.g. key_value or equivalent column) for each key.

// InslyDetailRepository::fetchSaveToImcrm (simplified) // Advisor fallback when Insly has no renewer $tempSalesPersonId = app(ApplicationStorageService::class)->getValueByKey(ApplicationStorageEnums::INSLY_TEMP_SALES_PERSON_ID); $tempPolicyId = app(ApplicationStorageService::class)->getValueByKey(ApplicationStorageEnums::INSLY_TEMP_POLICY_OID); if ($tempSalesPersonId && $tempPolicyId && (int) $tempPolicyId === (int) $policyID) { $advisorId = $tempSalesPersonId; } // Customer email fallback when policy has no customer.email in Insly $tempCustomerEmail = app(ApplicationStorageService::class)->getValueByKey(ApplicationStorageEnums::INSLY_TEMP_CUSTOMER_EMAIL); $tempCustomerPolicyId = app(ApplicationStorageService::class)->getValueByKey(ApplicationStorageEnums::INSLY_TEMP_CUSTOMER_POLICY_OID); if (empty($email) && $tempCustomerPolicyId && (int) $tempCustomerPolicyId === (int) $policyID) { $email = $tempCustomerEmail; }

Important: The matching is by policy OID (the Insly policy identifier). So only the legacy policy whose policy_oid matches the stored OID gets the temp advisor or email. This keeps the behaviour predictable and safe when moving multiple policies over time.

🔄 Move to IMCRM Flow

From the Legacy Policy detail page, the user clicks Move to IMCRM. The backend (LegacyPolicyController::moveToImcrm → InslyDetailRepository::fetchSaveToImcrm) runs the following logic. The controller returns the repository response directly (JSON).

1

Resolve email & advisor

Use policy customer email or Application Storage temp email; resolve advisor from Insly (renewer_person or quote.broker → InslyAdvisor) or Application Storage temp sales person ID. If email or advisor is missing after fallbacks, return 400.

2

Resolve quote type & model

Map policy.coverage to quote type via getQuoteTypeFromCoverage (InslyDataService). Get model via getModelObject($quoteType). If no model (unsupported coverage), return 400 "Quote Type not found."

3

Match by policy number

Search quote by policy_number or previous_quote_policy_number. If found and validateAll is true, return 200 type: 'policy_number' with data[0].link and code (modal: open existing lead). If found but validateAll is false, the same 200 is still returned.

4

Match by email + payment date

Only when validateAll is true: join quote table with payments, filter by email and captured_at between policy issue_date −1 month and +1 month. If any quote found, return 200 type: 'email' with data array (modal: user picks one or "Create new").

5

Create new lead

If no match: build payload via prePareData() (includes Application Storage email fallback), set advisor_id, create main quote, then create/update LOB-specific detail with insly_id (e.g. CarQuoteRequestDetail, HealthQuoteRequestDetail, quoteDetail for personal LOBs). Set moved_to_imcrm, imcrm_link, code, moved_to_imcrm_date, moved_to_imcrm_by on the Insly document. Sync to CAPI/personal quote where applicable. Return 201 "Lead Created Successfully".

Supported LOBs (Move to IMCRM)

The quote type is derived from the policy’s coverage via InslyDataService::inslyInsurances(). Supported LOBs for lead creation include: Business (incl. Group Medical, CorpLine), Car, Life, Home, Travel, Health, Pet, Bike, Cycle, Yacht, Savings. If the coverage does not map to a known quote type, getModelObject returns false and the API returns 400 "Quote Type not found."

Request Payload (Frontend)

POST /legacy-policy/move-to-imcrm { "policy_oid": 12345, "validateAll": true, "isInertia": true }

validateAll: true (default) runs policy number match and email+payment-date match; if matches are found, the frontend shows a modal (open existing or create new). validateAll: false is used when the user chooses "Create new" in the modal—the backend skips returning existing leads by email+date and proceeds to create a new lead when no policy number match exists.

Response Types

Status Type Meaning
200 policy_number Existing quote found by policy number; data[0].link, data[0].code; frontend shows modal with link to open.
200 email Existing quotes found by email + payment date; data array (each item has link, modelType, etc.); user can select one or choose "Create new" (frontend then calls move-to-imcrm with validateAll: false).
201 — New lead created; message "Lead Created Successfully".
400 — message: "Customer email not found." / "Advisor not found." / "Quote not found." / "Quote Type not found."

📂 InslyDetailRepository & Legacy Data

App\Repositories\InslyDetailRepository works with the InslyDetail model (MongoDB). Static-style calls (e.g. InslyDetailRepository::getDataByIndex()) are forwarded to fetch* methods by BaseRepository.

Method (called as) Implementation Purpose
getDataByIndex() fetchGetDataByIndex Search legacy policies. Only runs when the request has at least one of: policy_number, email, mobile_no (index action passes request to repository). Filters: exact policy_no, free-text customer.email, regex/wildcard customer.mobile_phone, and policy.coverage IN user’s coverage list. Uses MongoDB Atlas Search index insly_search_index. Returns paginated structure: data, current_page, per_page (15), from, to, next_page_url, prev_page_url. If no filter is sent, controller returns empty policies array.
getBy('_id', $id) / getBy('policy_no', $number) fetchGetBy Load one policy by column and value. If request()->policy_oid is set, also matches policy_oid (orWhere). Uses firstOrFail() → 404 if not found. Masks customer.email, customer.mobile_phone, customer.phone in response. Sets quoteType (from coverage) and imcrm_link (current app URL). Premium from sum of installments.gross_premium if present.
saveToImcrm($request->toArray()) fetchSaveToImcrm Run Move to IMCRM: resolve email/advisor (including Application Storage), match by policy number or email+payment date, or create new lead; update Insly document with moved_to_imcrm, imcrm_link, code, moved_to_imcrm_date, moved_to_imcrm_by.

Deprecated: fetchGetData() is a fallback listing implementation (non–Atlas Search, simple filters and whereIn('policy.coverage', $coverage)). Not used by the index when getDataByIndex is used.

Coverage / LOB Filtering (getCoverageList)

getCoverageList($user) returns the list of Insly policy.coverage values the user is allowed to see. It uses InslyDataService::inslyInsurances() and the user’s roles. Each role adds its coverages to the list:

  • BikeAdvisor → Bike; CorpLineAdvisor → Business; CarAdvisor → Car; LifeAdvisor → Life; HomeAdvisor → Home; TravelAdvisor → Travel; HealthAdvisor → Health; CycleAdvisor → Cycle; PetAdvisor → Pet; YachtAdvisor → Yacht; SavingsAdvisor → Savings.

Coverage values are merged and lowercased for matching. Search (getDataByIndex) only returns policies whose policy.coverage is in this list. Users with none of these roles get an empty coverage list, so the coverage filter is omitted and other filters (policy_number, email, mobile_no) still apply.

🗺️ Product & Coverage Mappings (LegacyPolicyEnum)

App\Enums\LegacyPolicyEnum defines two mappings used for display on the Legacy Policy list (Index) and for resolving quote type when moving to IMCRM. The controller passes legacyPolicyMapping (INSLY_PRODUCT_MAPPING) and coveragePolicyMapping (INSLY_COVERAGE_MAPPING) to the Index page.

INSLY_PRODUCT_MAPPING

  • Maps Insly product strings (e.g. "casco", "home insurance", "pet insurance") to display labels (e.g. "Motor Insurance", "Home Insurance", "Pet Insurance").
  • Used in Index.vue productName(item): first checks item.product.product against this map (lowercased).

INSLY_COVERAGE_MAPPING

  • Override for specific coverages: "motor fleet" → "Business Insurance", "casco" → "Motor Insurance", "group medical insurance" → "Group Medical Insurance".
  • In productName(item), if product is not set, item.policy.coverage is checked against INSLY_COVERAGE_MAPPING first, then INSLY_PRODUCT_MAPPING, so coverage-based display is consistent.

Quote type for Move to IMCRM is determined by InslyDataService::inslyInsurances() and getQuoteTypeFromCoverage($coverage), not by these enum mappings directly.

📎 Other Legacy Policy Features

Document Viewing (S3 Temp URL)

Legacy policy documents stored on the insly_documents disk can be viewed via a temporary URL. Frontend calls POST /legacy-policy/get-s3-temp-url with body { legacyPolicyId, fileName }. Backend checks Storage::disk('insly_documents')->has($fileName); if the file exists, returns { "url": "…" } with expiry 40 minutes (now()->addMinutes(40)). Otherwise returns { "error": "File does not exists on server" }. This endpoint has no permission middleware; access is effectively limited by the fact that fileName and legacyPolicyId are obtained from the Legacy Policy Show page (which is protected by VIEW_LEGACY_DETAILS or VIEW_ALL_LEADS).

Migrate Policy (CAPI)

POST /migrate-legacy-policy/{poid} sends { "policyIds": [poid] } to CAPI /api/migrate-policy. This is a separate migration path (e.g. bulk/data migration), not the same as "Move to IMCRM". Success: response must have result array with at least one item; result[0]['msg'] is shown (or "Failed!"). If msg == 'Failed!', redirect back with error; otherwise redirect back with success flash. The Migrate (POID) form on the Legacy Policy index page is only visible to users with MIGRATE_INSLY_LEAD permission.

View Legacy Policy from Quote Pages

Many quote show pages (Car, Health, Travel, Life, Home, Pet, Bike, etc.) show a "View Legacy policy" link when the quote has an insly_id. The link goes to /legacy-policy/{insly_id} (Legacy Policy show page; insly_id is the MongoDB _id). The route GET /legacy-policy/{policyNumber}/policy is named view-legacy-policy.renewal-uploads and is used to open a legacy policy by policy number (redirects to show by _id).

prePareData (New Lead Payload)

When creating a new lead, prePareData($policy, $quoteType, $isPersonalQuote) builds the payload. It uses getPrimaryAndAdditionalEmails / getPrimaryAndAdditionalMobileNumbers from the policy; if INSLY_TEMP_CUSTOMER_POLICY_OID equals policy['policy_oid'], it overwrites email with INSLY_TEMP_CUSTOMER_EMAIL. Other fields: previous_quote_policy_number, policy_number, dates, insurer → insurance_provider_id via InsuranceProviderRepository::getInslyProviderId, customer name split into first/last, default mobile_no 0552244556 when missing, CustomerService::createCustomerIfNotExists and additional contacts, CAPI for uuid and code, source = INSLY, insly_migrated = true, quote_status_id = NewLead. Business quotes get business_type_of_insurance_id from coverage.

✅ Summary

  • Legacy Policy = Insly (MongoDB) policies viewable and actionable in IMCRM. Index shows search results only when at least one of policy_number, email, mobile_no is provided (15 per page); show uses MongoDB _id; S3 temp URL (40 min) for documents; CAPI migrate for /api/migrate-policy. Permissions: VIEW_LEGACY_DETAILS or VIEW_ALL_LEADS for list/show/move; MIGRATE_INSLY_LEAD for Migrate form visibility.
  • Move to IMCRM = Resolve email and advisor (Insly first, then Application Storage), resolve quote type from coverage, match by policy number or (if validateAll) by email + payment date ±1 month, or create new lead. New lead: prePareData payload, LOB-specific detail with insly_id, then update Insly document (moved_to_imcrm, imcrm_link, code, dates, user). Supported LOBs: Business, Car, Life, Home, Travel, Health, Pet, Bike, Cycle, Yacht, Savings.
  • Application Storage keys INSLY_TEMP_SALES_PERSON_ID + INSLY_TEMP_POLICY_OID assign an advisor user ID to a specific policy OID when Insly has no renewer; INSLY_TEMP_CUSTOMER_EMAIL + INSLY_TEMP_CUSTOMER_POLICY_OID assign customer email when the policy has no email. Used in fetchSaveToImcrm and prePareData. Seeder creates placeholder rows; admin must set real values.
  • InslyDetailRepository: getDataByIndex (Atlas Search, user coverage filter, pagination), getBy (single policy, optional policy_oid in request, masking), saveToImcrm (full Move to IMCRM). getCoverageList builds allowed coverages from user roles (BikeAdvisor, CorpLineAdvisor, CarAdvisor, LifeAdvisor, HomeAdvisor, TravelAdvisor, HealthAdvisor, CycleAdvisor, PetAdvisor, YachtAdvisor, SavingsAdvisor). fetchGetData is deprecated.
