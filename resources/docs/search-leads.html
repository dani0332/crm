🔍 Search Leads

Cross-LOB search for leads and send-update (endorsement) requests, with role-based data scoping and export

✓ Active Feature

❓ What is Search Leads?

Search Leads is a global search that lets authorised users find leads (personal quotes) and send-update (endorsement) requests across all lines of business. Results are filtered by the current user’s role: advisors see only their own leads; managers see leads of advisors in their team; users with the search permission see data according to the same rules. Search runs against the read replica (readonly_db middleware) to avoid overloading the primary database.

💡 Two Modes

Lead List: Searches personal_quotes (main leads). Columns include Ref-ID, Private Client, First/Last Name, Company, Line of Business, Created Date, Policy Expiry, Policy Number, Status.
Send Update List: Searches send_update_logs (endorsement requests). Same base fields plus SU Ref-ID, Type, Sub type, Notes, Status. Toggle via the "Lead List" / "Send Update List" button; the list query parameter is leads or endorsements.

🔐 Permissions

Access to the Search Leads page and export is controlled by the following permissions. The routes themselves do not enforce permission middleware; they rely on the same auth middleware as the rest of the app. The sidebar "Search" link is only shown when the user has the required permission, so in practice only users with that permission can reach the page.

Permission Constant Purpose
Search (page access) SEARCH_ALL_LEAD_LOB Required to see the "Search" item in the main navigation. Without it, the user does not get a link to the search-leads page. Typically named "search-all-lead-lob" in the database.
Export to Excel DATA_EXTRACTION_SEARCH_ALL_LEADS Required to see and use the "Export to Excel" button on the Search page. Export is only available when there are results. Typically named "data-extraction-search-all-leads".

Both permissions are often assigned together for roles that need full search and export (e.g. in RolePermissionSeeder, searchAcrossLOBsPermissions includes both). A user with only SEARCH_ALL_LEAD_LOB can search and view results but will not see the Export button.

📍 Routes & Middleware

Endpoints

  • GET /search-leads – Renders the Search page (Inertia). Route name: search-leads. Query parameters: all filter fields plus list (leads|endorsements), page, sortBy, sortType.
  • GET /search-all-export – Downloads an Excel file of the current search result (same query string as the page). Route name: search-export. Uses ExportSearchLeadsOrEndorsementsRequest for validation.

Middleware

  • Both routes are inside the readonly_db middleware group (SetReadDbConnection). All queries run against the read replica.
  • No permission middleware is applied on the controller; visibility is via the sidebar (SEARCH_ALL_LEAD_LOB) and Export button (DATA_EXTRACTION_SEARCH_ALL_LEADS).

⚙️ Search Behaviour

When Results Are Returned

SearchService::getSearchLeads() returns no data when request()->except('list') is empty—i.e. when the only query parameter is list (or there are no query parameters). So the first load of the page (no filters) shows an empty table. The frontend requires at least one filter before running a search and shows a validation message: "Please select at least one filter before performing the search."

Authorization (Who Sees What)

After applying filters, the service applies role-based scoping in applyAuthorizationFilters():

  • Advisor role (e.g. CarAdvisor, HealthAdvisor, …): only leads where personal_quotes.advisor_id = current user id.
  • Manager role (e.g. CAR_MANAGER, HEALTH_MANAGER, …): only leads where advisor_id is in the list of advisors under that manager (via TeamHierarchyTrait::getAdvisorsByManagers()).
  • Users who are neither advisor nor manager see no extra restriction (e.g. admin / roles with SEARCH_ALL_LEAD_LOB may see a broader set depending on joins).

Universal Search Flag

The frontend checks isUniversalSearchEnabled (from Application Storage key ENABLE_UNIVERSAL_SEARCH). If it is disabled and the user does not have the Engineering role, the frontend blocks submit and shows: "Search is disabled as data migration is not completed yet!". So search can be turned off for most users until migration is complete; only Engineering can still run searches when the flag is off.

Troubleshooting

  • No results / empty table: Ensure at least one filter is set; if using filters that trigger the date requirement (e.g. quote status, line of business), set date type and date range.
  • Search blocked: If "Search is disabled as data migration is not completed yet!" appears, either enable ENABLE_UNIVERSAL_SEARCH in Application Storage or ensure the user has the Engineering role.
  • Fewer results than expected (advisor/manager): Advisors see only leads where they are the advisor; managers see only leads of advisors in their team. Users with no advisor/manager role have no extra scope.
  • Export disabled: Export button is shown only with DATA_EXTRACTION_SEARCH_ALL_LEADS and when the current result set has at least one row.

🔎 Available Filters

All filters are optional, but at least one must be set to run a search. For most filters, if code (Ref-ID) is set, some other filters are skipped (exact Ref-ID search). When certain filters are used (e.g. insured name, quote status, line of business), the frontend and export validation require a date type and date range.

Parameter Description
list leads or endorsements (required for export).
code Ref-ID (exact match on personal_quotes.code). When set, many other filters are not applied.
insured_name FULLTEXT search on customer insured_first_name, insured_last_name (join on customer).
member_first_name, member_last_name Member name; FULLTEXT on customer_members.first_name, last_name. Requires line_of_business (join depends on LOB).
company_name FULLTEXT on insured.company_name (join on insured).
policy_number Exact match on personal_quotes.policy_number.
mobile_no Exact match on personal_quotes.mobile_no.
email Exact match on personal_quotes.email.
su_code Send Update ref (exact match on send_update_logs.code). For lead list, joins send_update_logs.
date_type + date_range Date type: created_at, payment_due_date, payment_date, transaction_approved_at, policy_booking_date, policy_start_date, policy_expiry_date. Range: [start, end]. Payment dates join payments (and payment_status_log for payment_date).
quote_status Array; personal_quotes.quote_status_id IN.
payment_status Array; joins payments and filters by payments.payment_status_id.
line_of_business Array; personal_quotes.quote_type_id IN.
business_insurance_type Array; personal_quotes.business_type_of_insurance_id IN.
currently_insured_with Array; personal_quotes.insurance_provider_id IN.
department Array; join users as advisor, filter by advisor.department_id IN.
advisors Array; personal_quotes.advisor_id IN.
support_users Array; personal_quotes.support_user_id IN.
insurer_tax_invoice_number, insurer_commission_tax_invoice_number Tax invoice numbers (payments or send_update_logs depending on list).
update_status Send Update list only; send_update_logs.status IN (formatted uppercase with underscores).
send_update_type Send Update list only; send_update_logs.category_id IN.

Sorting: sortBy (default updated_at) and sortType (default desc) are applied on the base table (personal_quotes or send_update_logs). Pagination: 15 per page, page in query string.

Auto date-range requirement

When any of the following filters are used (without company_name), the frontend and export validation require date type and date range: insured_name, member_first_name, member_last_name, quote_status, payment_status, line_of_business, business_insurance_type, currently_insured_with, department, advisors, update_status. Otherwise the user sees "Date range is required for the selected filters" and export validation fails with the same message.

📤 Export

The Export button is visible only when the user has DATA_EXTRACTION_SEARCH_ALL_LEADS and there are results. Clicking it opens /search-all-export with the same query string as the current page, which triggers a download of an Excel file (SearchLeadsEndorsementsExport). File name: InsuranceMarket.ae™ Lead List <date>.xlsx or InsuranceMarket.ae™ Send Update List <date>.xlsx.

ExportSearchLeadsOrEndorsementsRequest validates: list required; at least one filter (besides list/page/sortBy/sortType) required; when date-type filters are required by the chosen filters, date_type and date_range must be present. Export uses the same getSearchLeads($isEndorsementList, true) so it returns all matching rows (no pagination) with extra columns (e.g. advisor name, support user name, insurance provider, PCP tag, payment total).

After building the export data (on the read replica), the controller calls DB::setDefaultConnection('mysql') and CentralService::generateExportLogs() so that export activity is logged on the primary database. The file name date format is config('constants.DATE_DISPLAY_FORMAT').

📂 Implementation Notes

  • Controller: App\Http\Controllers\V2\SearchController – index() (Inertia Search/Index), searchExport() (Excel download).
  • Service: App\Services\SearchService::getSearchLeads($isEndorsementList, $isExport) – builds query from request, applies joins/filters, authorization, sort, then paginate (15) or get all for export.
  • Frontend: resources/js/inertia/Pages/Search/Index.vue – filters, Lead vs Send Update toggle, table, export button (permission-gated), URL state via useUrlSearchParams('history').
  • Export class: App\Exports\SearchLeadsEndorsementsExport.
  • Base table: personal_quotes (lead list) or send_update_logs (endorsement list); joins include quote_type, quote_status, customer, business_type_of_insurance, and conditionally insured, payments, users, etc.

✅ Summary

  • Search Leads = global search across leads (personal_quotes) or send-update logs (endorsements), with role-based scoping (advisor / manager) and read-replica usage.
  • Permissions: SEARCH_ALL_LEAD_LOB to see the Search nav link and use the page; DATA_EXTRACTION_SEARCH_ALL_LEADS to see and use Export to Excel.
  • Routes: GET search-leads (page), GET search-all-export (Excel); both under readonly_db middleware.
  • Behaviour: No params ⇒ empty result; at least one filter required (frontend validation); optional Universal Search flag (ENABLE_UNIVERSAL_SEARCH) blocks non-Engineering users when disabled.
  • Filters: Ref-ID, insured/member/company name, policy number, contact, dates, statuses, LOB, department, advisors, support users, tax invoice numbers, and (for endorsements) update status and send update type.
